## Streams and the Stream panel

The home page puts streams on a card grid or a list, with a 2/4/9 split-screen switch in the top-right corner so several streams sit side by side on one workbench and every cell can @-assign work directly. Creating a stream and joining by UUID open from the panel's top bar. Virtual employees, Market, the dispatch console, the virtual inbox, VMs and Settings all live in the top navigation bar. A stream's border flashes with task status: **yellow** means work was @-assigned and is still queued for a time slice, **green** means a virtual employee just claimed it and advanced the stream (a finished green is kept for a few seconds). The rhythm follows human feel — yellow at 0.65s (≈ exercise heart rate), green at 1.8s (≈ resting heart rate) — and each stream can change its two colors under Settings → Blink color; the preference is stored only on the local machine.

To the right of the chat are two collapsible cards. The **stream announcement** can be published and cleared, shows its update time and is read-only for non-admins. **Stream files** preview online, download, upload and delete, stored as text capped at 400KB; an upload broadcasts a system message, a `.drawio` flowchart previews as a structure diagram (nodes, edges and labels only — styles and coordinate precision are not restored) and everything else previews as plain text; Settings → Stream announcement keeps only a pointer sentence so two places never edit the same field. Below the two cards are the Members / VMs / MCP / Settings tabs. A stream file a virtual employee hands in this round hangs under its reply as a **delivery card** (name, size, type and one delivery note); the whole block opens that original in the stream files view, and a round that delivered only files with an empty body still sends the card — a card with no bubble. Every announcement and file operation is also available through MCP tools (see "Skills, Market and MCP").

A machine that was granted in the stream and has a console gateway filled in adds an **SSH console** entry to the top bar, and every row of the settings drawer's "machines attached to this stream" column opens it directly: a real split screen on a wide window (chat and input stay usable on the left, an iTerm-style terminal on the right), and on a narrow container the terminal covers the stream until closed. The console dials the ttyd gateway on that machine, recommended started as `ttyd -p 7681 tmux new-session -A -s work` — then you and the virtual employee attach the same tmux session, so you can `dmesg -wT` and `ls` to watch the scene while watching what they do. Remote desktop is not on this chain.

## Virtual employees and delivery status

Both human and virtual employees can set an avatar: upload under Settings → Account or in the Virtual employees profile, and the browser crops it to a 128×128 WebP stored in the database, with the stream, member lists, dispatch console and top navigation all following; with no avatar set it falls back to the first letter of the name. Without an image at hand you can click the row of built-in default avatars below the upload button (boys: short hair / side part / glasses; girls: long hair / shoulder length / ponytail) — they are SVGs in `src/lib/avatars.ts`, baked into the same 128×128 WebP only on click, so the stored column, the `avatarData` validation and the upload path are exactly the same, and the repo holds no avatar image files.

Clicking any virtual employee's avatar opens the `#/agents/<id>` detail page: which message their virtual inbox is processing, how many mails are queued, a spinner on the corner while busy, and the signature in small quoted text next to the avatar. Every @ message carries this employee's delivery status — queued = **unread**, started = **processing**, finished = **read**, failure and cancellation marked separately. The owner can change the signature on the Virtual employees page, and the employee can update it with `set_signature` inside its tool loop. A non-owner opening the detail page sees only what stream members already see — the profile and presence in shared streams; keys, system prompts and memory never appear.

Below "which message is being processed" the page draws a **Stream flow**: the horizontal axis is when each mail entered the time slice, the vertical axis lists streams by weight, high to low; each mail is a bar — processing is a yellow bar with a flowing highlight, read is colored by stream, unread is dashed, failed is red. The window takes the last 15 minutes or 24 mails, and the owner and stream mates see the same chart (stream mates see only shared streams). The card's footer carries a **cache hit** statistic that sums each step's `input_tokens / cached_tokens` by stream: the overall hit rate is token-weighted, not an average of per-round percentages, and box-selecting a time range counts only that range. The method lives in `src/lib/usageStats.mjs` (the `.mjs` extension lets `dev/smoke.mjs` import the very same implementation instead of copying the algorithm into the test): rounds where upstream reported no usage — cut off by an interrupt, QCA cloud, the demo backend — stay out of the denominator, self-contradictory usage is collapsed to `null` at the storage step (`normalizeUsage` in `functions/agents.mjs`), and when there is no usage at all the bar says "this backend does not report usage" rather than passing off 0%.

## Delegates

A delegate only **answers on behalf**, it never **collects on behalf**. In Settings' Delegates card pick one virtual employee under your own name and an effect window — "start immediately" or "a time window" (up to 90 days out, either end can be left alone) — and the roster takes effect across all streams under that name at once. When a stream @-mentions the human, the notification is still delivered to the human (virtual inbox or real email); the delegate merely receives one **extra** task. The reply is still signed by the delegate, with an "answering on behalf of @X" tag on the bubble that comes from `messages.on_behalf_of`, never from renaming anyone. The stream-settings drawer can toggle the delegate for that stream only or switch to another employee. Whether it applies is computed from the clock at dispatch time, never by changing state at a deadline: when the window ends, answering simply stops, and no resident process has to guarantee that "closing the sign" happens. The delegate must belong to you, be running and already be in the stream — borrowing someone else's employee to speak for you would let a third party read your stream context, and it is refused on the spot.

## Schedules

Virtual employees can **work on a schedule**, without waiting to be @-ed. In the dispatch console's Schedules card, put an "every interval" (1 minute to 7 days) or "daily at" schedule (time + weekdays + a UTC offset, the local offset brought in by default and tagged "local", half-hour steps supported) on a given (employee, stream) pair, then write what needs doing (up to 2000 characters). After saving, the row shows the next three due ticks computed server-side, when the last run happened, and the cumulative count of merged ticks. A due round still goes through the same time-slice pipeline: the schedule merely posts one more mail into that employee's inbox, and concurrency slots, CAS claim, interrupts and compaction are all reused. When someone is online waiting for an answer the human is answered first, and the schedule catches up by clock in the next round; a round with nothing to say may reply with an empty body, and WorkStream will not post a "nothing this time" into the stream for you. At most 20 schedules per person and a minimum interval of 1 minute — proactive work is not a timer for flooding a stream. Pausing writes the clock column empty and the UI then shows "next due —" instead of pretending it still runs; editing the text will not reopen a schedule you stopped yourself. Deleting a schedule retracts the queued mail that has not run (the one already generating runs to the end — cutting it off is an interrupt's job). Removing an employee from a stream stops that stream's schedule, and deleting the employee or dissolving the stream cascades to the schedules hung on them. Schedules can only be made for employees under your own name and streams you are in — scheduling someone else's employee burns someone else's key and is refused on the spot.

## Global memory (dreaming)

Virtual employees of one person often work in several streams at once, and each stream's history folds into its own summary — cross-stream facts ("this project ships at month end", "we agreed on psql, no ORM") sit scattered with nobody merging them. **Global memory (dreaming)** feeds the current compaction summaries of all the owner's streams to the model once and merges them into one memory belonging to that person, which returns as an independent block into the context of every stream under that name in the next round (before the cache breakpoint, reused verbatim in steady state, adding no per-round cost). There are three entry points and all go through one merge path: **merge when a stream's history finishes folding** (the switch on the dispatch console's "Global memory" card, hung on the person rather than the employee, because the merged result belongs to the person), **merge on a schedule** (a "merge global memory at due tick" schedule, whose body text is an extra instruction rather than required, and whose round does not speak in any stream), and **run one merge manually here**. The three share one deduplication: only one merge mail per person may be queued at a time, so double-clicking and a fold colliding with a schedule are the same thing — nothing new except paying one call. The watermark is kept per (employee, stream): when two people in one stream each fold a summary, recording per stream alone would let the later write override the earlier sequence number and that entry would either re-merge every round or be treated as merged and lost. Summaries that do not fit the input budget are honestly recorded as "not merged in this step", the watermark does not advance and next round they are still new material; an upstream error or an empty-body reply means not one stream was merged, so no watermark field is written and nothing already landed by someone else is overwritten (compare-and-write). Cross-stream privacy is a hard boundary: that memory is for the model's judgment only, its header is hardcoded to "do not recite another stream's details to this stream", it never enters a stream body, and others reading their own copy read emptiness.

## Skills, Market and MCP

Built-in skills are written in `functions/skills.mjs` — never stored in the database, never uninstallable, always injected into every virtual employee's context: the **WorkStream platform skill** (creating a stream, pulling in employees, inviting humans, sending messages, registering and authorizing VMs, reading history and the announcement) and **DevStream stream files and announcements** (browsing, previewing, uploading and deleting stream files and reading and writing the announcement, including `tools/call` examples for the external MCP). Two public default skills (weekly report and progress sync, meeting notes and action items) are filled in idempotently by fixed ids and installed automatically when a new employee is profiled.

Market has two tabs. **Skills** does not expand details by default: one line per entry with name, version, category, a one-line summary and a `.md` download link, the body shown only on click. The local market (uploaded on this site: public, settable as a default skill for new employees, installable to chosen employees) and the remote skill sources each take a sub-list, and search by name/summary/category lists entries the same way. Install targets: one chosen employee, all existing employees, or "existing + future employees" (which marks the skill as default and auto-installs it for new employees); the Skills tab of an employee detail can also search the local market and remote sources, but what it installs goes only to that one employee, and uninstalling happens in the same tab. Built-in skills show no install control — they are always enabled. **Plugins** connect external standard MCP services (JSON-RPC over HTTP): the server probes `tools/list` and caches the inventory, the tools are merged into the inventory of every virtual employee under the owner, and calls go through the same tool pipeline and land in the trajectory. Tokens are stored as ciphertext and the UI returns only their tails; endpoints pass SSRF validation (only https in production, internal networks only with `WORKSTREAM_DEV=1`). At most 12 connectors per person and 24 tools per connector; a built-in tool wins a name collision.

Remote skill sources (`functions/registries.mjs`) are addresses the owner adds: at most 8 per person and 200 entries per source. A source is an index JSON with `schema: 1` — `{ name, skills: [{ slug, name, summary, category, version, body_url }] }` — where `body_url` points at a `.md` body on the same host, so a GitHub repo or static site holding `index.json` plus a few markdown files works as a source. Version numbers are display-only; comparisons take dot-separated numeric segments one by one (`1.10` is newer than `1.2`), and a non-numeric version counts as an update whenever it differs. A remote install means "copy a snapshot": at install or update the body is written into a local `skills` row along with its source (`source_registry_id` + `source_slug`) and version, and whatever upstream changes afterwards does not affect the employees using it. There is exactly one snapshot row per owner + source + slug, shared by several employees, so an update replaces the body once and every employee that installed it switches at the same time. Opening an employee's Skills tab pulls each source's index once to self-check versions (or click re-check versions); entries with an update show the target version and an update button, and an unreachable source only notes that those remote skills cannot be version-checked right now, without affecting injection of what is already installed. Fetch boundaries: index and body are time- and byte-limited (256KB / 200KB), redirects are refused, the body must be same-origin with the index, and only https in production.

Available in an employee's tool loop: `search_history / read_window / list_files / read_file / upload_file / delete_file / present / get_announcement / get_context / list_skills / read_skill / list_my_resources / set_signature`, plus `send_message / create_stream / add_agent_to_stream / invite_member / set_announcement / register_vm / grant_vm` executed as the owner. Write operations are checked against the owner's role in the stream and resource ownership; `set_signature` changes only the employee's own signature and is not open to the external MCP. `present` marks one file of this stream as this round's deliverable and only makes sense inside the employee loop — the card must hang on the reply of that very turn, and an external MCP call belongs to no turn, so it is not in the external inventory.

The external MCP endpoint (`POST /functions/v1/app?action=mcp`, authenticated by `x-workstream-mcp-key`) is scoped to that stream and exposes 13 tools: stream history, context, announcement reading, stream file list/read/upload/delete, and `send_message / invite_member / set_announcement / list_skills / read_skill`. Creating streams and registering or authorizing VMs are available only inside the employee tool loop.

## Cloud Agent backend (Qoder Cloud Agents)

The **model source** on the Virtual employees page defaults to a self-hosted OpenAI-compatible endpoint; you can also pick **Qoder Cloud Agents**, where the employee carries no model of its own and hangs on an existing agent in Qoder Cloud Agents. When creating the profile, paste either `agent_…` or the whole console link (the id is taken from `https://qoder.cn/cloud/agents/agent_xxx`); switching the address field to cloud fills in the CN-region origin (change it for another region or a private deployment), and the token is a `pt-…` created under Qoder Settings → Personal Access Tokens, sealed with AES-GCM into the database as before with only its tail returned. Switching backends must come with a new token — a self-hosted endpoint's `sk-` key is not recognized in the cloud, and the server refuses outright with `agent_key_required_for_backend`.

This channel differs from a self-hosted endpoint in three deliberate ways:

- **The context authority stays in WorkStream**: each round compresses the common memory, this stream's memory, the window after the summary watermark and the skill instructions into a single `user.message` (role segments marked; over 900,000 characters is blocked before egress). The cloud session is only the cloud-side conversation cache, one per (employee, stream) in `app.qca_sessions`, so streams never bleed into each other on the cloud; removing the employee from a stream, rebinding another cloud agent, or changing address or token invalidates and rebuilds the cache. The background compaction round uses a one-shot session, so "summarize for me" never mixes into stream history.
- **The tool loop is in the cloud**: our stream tools are not injected and the cloud agent uses its own tool set. The skill instructions in its context therefore change wording — "WorkStream tools are not reachable on this channel; do not write tool names into your reply; list any actions that need landing as a to-do" — so it does not fake-execute a `send_message` by following the skill body.
- **Thought chains do not enter the stream**: connect the SSE first, then ask, and take only `type=text` blocks from the canonical `agent.message`; thinking and tool blocks are dropped. Partial deltas are used only to hand over the body before the breakpoint on an interrupt; if the stream ends before a canonical reply arrives it honestly reports `qca_stream_ended_unfinished` / `qca_no_reply` rather than passing off deltas. Cloud errors, rate limits and dead tokens map to `qca_*` error codes in the trajectory, with the same "this didn't complete" notice as self-hosted endpoints. The thought-chain tab of the trajectory inspector is the only place to read it; when the backend returned no reasoning, that page says "this section is empty" instead of leaving a blank that looks broken.

Interrupt and stop use the same bar on both channels: it asks whether to stop on every chunk received and on every 800ms of silence. A cloud agent running tools on its side may emit no deltas for a whole stretch, and checking only at chunk boundaries would drag an interrupt toward the full 180s round timeout — both backends' `Interrupted` hand over the half body before the breakpoint. Upstream bad behavior is graded the same way on both: an SSE that ends with neither `[DONE]` nor `finish_reason` reports `upstream_stream_incomplete` on self-hosted channels, the same thing as the cloud's `qca_stream_ended_unfinished` — not one character of the half body enters the stream and the round closes as failed. Non-2xx is translated at egress into a named code (`upstream_server_error` / `upstream_rate_limited` / …), so no bare `"500"` lands in the inbox or the trajectory; one sentence has exactly one home in the error-code table. No path re-queues a `failed`, so the stream line says "to try again please @ them again", not "will retry automatically". Section 28 of the self-check pins all of this with a fault flag (500 / empty stream / truncated, switched per run, not by trigger keywords) plus a control that a re-@ after dialing back runs fine.

Backend differences live on one inventory table: in `functions/backends.mjs` each channel carries its own transport and `caps.tools`, and "does this channel take tools" is decided by that one field — prompt wording, whether the engine sends a tool inventory and whether the owner's connectors are consulted all read the same copy. A transport declared in the table but missing from `TRANSPORT_ROUTES` in `agents.mjs` throws at cold start, and the UI's Model source dropdown is cross-checked against the table by `npm run check:schema`. The built-in demo endpoint is the table's third channel: it is not a profile option — `api_base_url` equal to `demo://local` names it — so unworkable combinations such as "cloud backend + demo address" are blocked at profile creation and edit (`qca_needs_real_origin`). The connectivity test (`agents.test`) pulls the model inventory once in the cloud to confirm the token and address pair up, creating no session and touching no usage; the other channels send one very short conversation through the engine's dispatch fork. Real cloud integration needs a `pt-…` token; the self-check covers the same chain with a local fake QCA (section 23 of `dev/smoke.mjs`), and the inventory's own shape and parsing rules have section 8d3.

## Themes, languages and branding

Light and dark themes are controlled by `<html data-theme>` plus Tailwind `dark` variables; the first-frame script in `index.html` pre-sets it from the localStorage preference or the system preference to avoid a white flash. The `>_` in the top navigation switches between "solid block" and "inset" under Settings → Logo style — the inset one has a transparent background, a white glyph in the dark theme and a black one in the light — and the preference is stored only on the local machine. The copyright line `copy right www.void-universe.com` sits on the About page and the login page footer.

The UI languages are the deduplicated official/common languages of the top 26 economies by nominal GDP, listed as **18** (IMF WEO 2025 figures, April 2026 edition: en, zh-Hans, de, ja, hi, fr, ru, it, pt-BR, es, ko, tr, id, nl, ar, pl, sv, he). The set is decided by one inventory and lands in two places: the frontend [src/lib/i18n.ts](../src/lib/i18n.ts)'s `LOCALES` carries id, endonym, writing direction and "finished or not", while the backend [functions/locales.mjs](../functions/locales.mjs) carries only the id whitelist (an Edge Function cannot bundle the frontend TS, so the list exists twice and `npm run check:schema` cross-checks the two id sets, the dictionary keys and placeholders, and whether every key the UI looks up has a translation). **The first time you enter the site you are asked for a language once** (preselected from the browser language; whichever you pick, all screen text changes right there), and after login it is written to `users.prefs.lang` and read back on the next cold start — the account preference beats the local one, so switching devices needs no re-choice. Only Simplified Chinese, English, German and Japanese are finished, and the coverage is **the whole UI's copy**: the language step itself, login and signup, the verification-link landing page, the top navigation, Settings, and the chat, virtual employees, schedules, skills-and-plugins and trajectory-inspector pages — including the error codes returned by the backend (`upstream_rate_limited`, `schedule_not_owned`, and the family assembled from field names such as `invalid_token`, or `users_request_failed` assembled from the table name when the database is unreachable), because the reason "this round didn't run" is the sentence most in need of being understood. The remaining 14 are listed under "coming soon" but not clickable: an option that still shows Chinese gives no error at all, which is worse than not offering it; Arabic and Hebrew also wait for the right-to-left batch (`<html dir>` is currently always `ltr`).

**The UI copy is translated; the body text generated by the backend is half translated.** The system lines that land in a stream and the demo employee's conversational replies are decided at the moment of writing by the actor's `users.prefs.lang`, with the Chinese and English templates kept together in [functions/copy.mjs](../functions/copy.mjs) (an account that never picked a language falls back to Chinese, one that explicitly picked German or Japanese falls back to English — the odds of reading English are far better than the odds of reading Chinese). Virtual-inbox mails, compaction and merge summaries are still Chinese, and the explanation line on the Settings page draws exactly that line, without pretending they were translated along (an inline tag would require the backend to carry the provenance on the message — see the TODO table in [CHANGELOG.en.md](../CHANGELOG.en.md)). Deciding a system line's language by its writer costs one thing: when a stream's members do not share a language, the line shows the actor's — the thorough fix is storing a structured event and rendering it per viewer locale, which needs a column on messages plus a backfill of historical rows.

## How the backend works

The browser only calls the same-origin `/functions/v1/app?action=<name>` and carries no platform credentials. The session token rides in the custom header `x-workstream-token` — the site adapter strips the frontend's `authorization` and `cookie`, so those two headers cannot carry application-layer credentials (section 11 of `dev/smoke.mjs` runs the real `serveSite` and verifies that boundary).

Authentication is done at the application layer: PBKDF2-SHA256 password hashing (150,000 rounds), session tokens as sha256 digests (30 days), and API keys plus VM passwords sealed with AES-GCM (the master key prefers `WORKSTREAM_DATA_KEY` and otherwise lands in one row of `app.runtime_state`). Ciphertext columns are read only server-side and the API returns only the tail of a key. User-supplied API addresses pass the SSRF whitelist: only https in production, internal and metadata addresses refused.

Scheduling has two driving modes going through the same `scheduler.tick`. An edge function cannot stay resident, so a pure site deployment advances one tick per 5-second frontend poll (skipped while the page is hidden); local and self-hosted deployments can add `--worker` (or `WORKSTREAM_WORKER=1`) to bring up the resident loop of `functions/worker.mjs`, advancing the inbox with no frontend open. Each virtual employee's budget for the tick is split across streams by stream weight (confirmed by the stream owner/admin, equal by default) with the largest-remainder method; tasks are claimed with compare-and-write; running orphan tasks are caught by expiry reclamation; the @-between-employees depth limit is 3. A delegate opens no separate path: it posts one extra ordinary `mail` at dispatch, reusing time slices, CAS claim, interrupts and compaction. A schedule likewise opens no separate path: a due schedule is posted as a mail in the same tick, and the worker also scans due rows when not one mail is queued (keying only off "is any mail queued" means a quiet stream never accumulates the first one and its due schedules lie in the table waiting for a trigger that never comes); advancing the clock uses compare-and-write, so the frontend poll, the resident worker and multi-instance Functions all seeing the same row yield one winner, and a failed delivery rolls the clock back to the value just read so the next round re-decides the due tick.

## Deployment status

The frontend and the Function are verified locally by `npm run qa`. Cloud publication still needs two steps, and the current account's plan allows only static-site deployment and cannot enable a database and storage, so enabling the backend, applying the fourteen migrations 0001→0014 under `sql/` in order (the new tables alongside the base ones — `run_steps`, `plugins`, `skill_registries`, `qca_sessions`, `schedules` — plus incremental columns such as `messages.presented`, `memories.covers_streams`, `schedules.purpose`, `vms.gateway_url`) and publishing the full version with the backend are all stalled at the same point. The planned storage boundaries (application-layer auth, tables read and written by the site Function, keys sealed into the database with AES-GCM) are confirmed, and the disclosures still hold:

- The database tables are reachable from the Function; isolation against provider direct-access or bypass entry points has not been penetration-verified in a deployment environment.
- VM registration and connection probing are real (host/port/privilege level plus HTTP/TCP reachability), but the edge runtime has no raw TCP sockets, so the server never logs into SSH to run commands; passwords are stored only as ciphertext and never shipped to the browser. The **SSH console** runs on a different chain: the browser connects straight to the WebSocket gateway on that machine (the ttyd wire format), and WorkStream only stores the gateway address — it does not proxy the session and does not hand out credentials — so there is no server-side SSH channel to breach, at the price of keeping the gateway running on that machine by yourself.
- Email verification uses the development-mode inbox (the link appears directly in the UI); once `WORKSTREAM_SMTP_URL` is configured it switches to relay delivery.

`functions/` and `dist/` are ready to publish: `webDirectory: "dist"`, `functionDirectory: "functions"`, `databaseAccess: "read_write"`, `secretNames: ["WORKSTREAM_DATA_KEY", "WORKSTREAM_SMTP_URL"]` (both values are entered through site settings and both are optional).
