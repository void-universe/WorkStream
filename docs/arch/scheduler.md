# WorkStream 调度器架构

scheduler · executor · context assembly ｜ 实测日期 2026-11-02 ｜ 源码：`functions/engine.mjs`、`functions/worker.mjs`、`functions/bus.mjs`、`functions/chat.mjs`、`functions/agents.mjs`

**一页结论。** 调度层是「邮箱 FIFO + 跨群加权时间片」：群里 @ 一位虚拟员工 = 往 ta 的邮箱投一封信，`scheduler.tick` 按创建顺序取信、按群权重分并发槽、CAS 抢任务执行；服务端常驻 `worker` 让队列在没有浏览器时也往前走。执行层是「单发流式调用 + 插话掐断」：每轮把群历史现场重渲染成一条 system 消息发给 OpenAI 兼容上游，边收 SSE 边查插话。上下文层是「稳定前缀 + 尾部追加窗口 + 后台压缩」：块序即缓存序，窗口按字符预算分页取，压缩在后台把水位线推上去；实测两轮之间的可复用前缀 **98.5%**，每轮只为本轮新增的记录付 prefill。

本文第 6 节把已经查实的 8 个问题逐条列出，每条都给改前/改后的实测数字与对应的回归断言。

## 1. 端到端流程

```
群聊前端 / MCP
  messages.send：消息落 messages（seq 递增），解析 @ 提及，
  为每位被 @ 的虚拟员工插一行 mail（status=queued，priority=该群权重）。
      ▼
tick 驱动者（两个，可并存）
  · 服务端常驻 worker（functions/worker.mjs，--worker 或 WORKSTREAM_WORKER=1）：每 1s 一轮。
  · 群聊页轮询（ChatView.tsx）：每 5s 一轮，兜住没起 worker 的部署。
  两者共用同一个 scheduler.tick，认领是单行 CAS，同时跑不会重复执行。
      ▼
scheduler.tick（engine.mjs）
  reapStale 回收跑了 5 分钟以上的僵尸任务
  → 取 queued 信 → 过滤掉「同 (员工, 群) 已有 running」的那些，一轮只放最早的一封
  → 按员工分组、组内按群分组 → allocate() 分槽 → 并发执行。
      ▼
CAS 抢任务
  mail.claim(id, queued→running)，slice_count+1。多个驱动者并发时只有一个能抢到。
      ▼
runTask（engine.mjs）
  装配上下文 → 超预算先从窗口头部裁剪、并补投后台压缩信 → 调上游（SSE 流式）
  → MCP 工具回路 → 回复落群 → 写一条本群记忆 note。
      ▼
interruptWatcher（engine.mjs）+ bus（functions/bus.mjs）
  同进程插话/叫停走 bus 立即生效；跨进程由 400ms 的邮箱轮询兜底。
  发现比当前触发消息更新的插话就掐断上游（Interrupted 带已输出的半截），
  插话作为新触发重跑（≤2 次），叫停则任务置 cancelled。
```

## 2. 数据模型

| 表 | 键 / 约束 | 在调度里的角色 |
| --- | --- | --- |
| `mail` | `(agent_id, stream_id, status)` 索引 | 邮箱即任务队列。`status`: queued → running → done / failed / cancelled；`trigger_seq` 指向触发消息；`meta.interrupt` 存未消化的插话；`meta.kind="compress"` 是后台压缩信。 |
| `slice_prefs` | `UNIQUE(agent_id, stream_id)` | 该员工在该群的时间片权重 1–20（默认 1）。群主/管理员才能改。 |
| `memories` | `(agent_id, scope)`、`(agent_id, stream_id)` | `scope=common` 跨群长期记忆；`scope=stream` 本群记忆；`kind=summary` + `covers_through_seq` 是本群压缩摘要的水位线。 |
| `messages` | `(stream_id, seq)` | 群转录的唯一权威。上下文窗口、插话判定、审计回执全部以它为准。 |
| `cli_sessions`（规划） | `UNIQUE(agent_id, stream_id)` | per（员工, 群）的 CLI 会话键：runner / session_id / last_seq / workdir。见第 7 节。 |
| `run_traces`（规划） | `(mail_id, seq)` | 每次运行的 thinking / 工具调用 / 装配上下文快照。群里只看结论，过程在员工详情里点开看。 |

**平台约束（已核实）**：站点迁移接口只接受 `CREATE TABLE`、`ALTER TABLE ADD COLUMN` 和普通 `CREATE INDEX`。所以「每个 `(agent_id, stream_id)` 只允许一行 running」这种部分唯一索引做不出来，该不变量由调度规则 + CAS 认领承担（见 3.2）。

## 3. 调度算法

### 3.1 取信与分槽

- **群内 FIFO**：查询按 `created_at asc`，同一员工在同一群里严格按投递顺序处理。
- **跨群加权**：`allocate(budget, groups)`（最大余数法）把 `WORKSTREAM_SLICE_BUDGET`（默认 2，上限 8）个槽按 `slice_prefs.weight` 切给各群，且不超过该群实际排队数。
- **总并发上限**：`budget × min(员工数, 6)`，防止一轮 tick 打爆上游配额。
- **僵尸回收**：`reapStale` 把 running 超过 5 分钟的任务判 `failed: slice_interrupted`，并把期间收到的插话转成新 queued——插话不会因为进程死掉而丢。worker 在没有排队信时也跑这一步，否则崩溃留下的 running 会永远卡住那个员工。

### 3.2 一个（员工, 群）同时只跑一封

一轮 tick 先读出全部 running 信，拼成 `agent_id:stream_id` 集合，queued 信里命中集合的直接跳过（**不退而求其次**去跑同一对的下一封）。于是：

- 同一对并发跑两封时，后一封的上下文里没有前一封的回复，落群顺序还会倒置——这条规则把它挡住；
- 认领是 `queued→running` 的单行 CAS，两个驱动者（多 Function 实例、前端轮询、worker）同时看上同一封时只有一个赢，输的那个直接跳过，所以规则跨进程同样成立；
- 后台压缩信让位给真人触发的那封，否则压缩排在队头时每次回复都要多等一轮。

### 3.3 为什么默认 FIFO 就够

群聊里「先说先办」符合真人直觉，FIFO 让队头阻塞可预测；真正需要区分优先级的是跨群资源争抢，那部分已由权重时间片承担。等实测出现饥饿再上优先级队列。

## 4. 执行层：流式 + 插话

- 上游调用走 SSE，逐片累加 `delta.content`；**只累加正文**，推理模型的 thinking 字段不进群（群里只留思考后的结论）。
- 每收到一片就问一次 `interruptWatcher`：同进程由 `bus.mjs` 的 `fireInterrupt` 立即命中；跨进程由 400ms 的邮箱轮询兜底。命中就 `reader.cancel()` 并抛 `Interrupted{partial}`。
- 半截内容不丢：重跑时作为「上一条说到一半被打断」的提示喂回去；叫停则任务置 `cancelled`，半截不落群。
- 插话重跑上限 2 次，防止两个人轮流插话把任务变成死循环；超限按 cancelled 收尾并留回执。
- 接 CLI 执行器后，掐断语义从「cancel 读循环」变成「kill 进程组 + 从 stdout 增量捞半截」。

## 5. 上下文装配与压缩

### 5.1 块序即缓存序

`buildMessages` 每轮产出一条 system + 一条 user。提供商侧前缀缓存按「从头开始最长匹配」命中，所以稳定块在前、每轮必变的块一律压到最后：

| # | 块 | 变化频率 |
| --- | --- | --- |
| 1 | 身份（名字 / 角色 / 群名） | 几乎不变 |
| 2 | 个性签名 | 偶发 |
| 3 | 工作守则 | 几乎不变 |
| 4 | 群公告 | 偶发 |
| 5 | 技能清单 | 几乎不变 |
| 6 | 「如需更早记录请调工具」固定句 | 不变 |
| 7 | common 长期记忆（近 20 条，**升序**） | 尾部追加 |
| 8 | 本群压缩摘要 + 水位线 | 压缩时变 |
| 9 | 最近转录窗口（按字符预算，**尾部追加**） | 尾部追加 |
| 10 | 本群记忆 notes（近 30 条，**升序渲染**） | 常态下为空（见下） |
| 11 | 触发消息 | 每轮必变 |
| 12 | 插话提示 | 仅插话轮 |

7、9 两块用升序/尾部追加，是为了让新内容只追加到块尾，不打断已有前缀（降序会让每条新记忆改写块头）。

**第 10 块的取舍**：每回完一条就往本群记忆插一条 `#NN 回应：<正文前 200 字>` 的回声。装配时按序号两头剔除——`NN ≤ 水位线`的已经折进摘要，`NN ≥ 窗口头`的转录里就带全文，只有落在「摘要没覆盖、窗口又装不下」那段缝隙里的回声才单列。这块排在转录之后，而**前缀缓存是一刀切**：断点之后哪怕逐字节相同也算 miss，所以让它常态为空比让它变小更要紧（实测它一度占每轮 miss 的 86%，见 P9）。非回声类 note（压缩失败留痕、用户显式记下的事）没有序号，一律保留。

### 5.2 窗口锚点：回复取尾部，压缩取头部

`history()` 按页（200 行/页，最多 50 页）从水位线那一侧往回取，累计到字符上限为止，**不按条数截断**：

- **回复用 `anchor=tail`**：取水位线之后最新的一段（上限 = 预算 × 0.8）。被挤出去的旧记录靠 `search_history` / `read_window` 查，提示词里已经写明。
- **压缩用 `anchor=head`**：从水位线往后**连续**取一段（上限 = max(4000, 预算 × 0.12)）。这样 `older`（较老的一半）一定是水位线之后的一个真前缀，`covers_through_seq` 不会把没被摘要读过的记录算成已覆盖。

窗口取不满（`truncated`）时同一轮补投压缩信，把水位线推上去。

### 5.3 压缩在后台自己排空

压缩不在关键路径上：回复那一轮只做确定性的字符裁剪，压缩交给一封 `meta.kind="compress"` 的后台 mail。压缩信跑完时如果水位线之后还压着记录，**自己续投下一封**（先 `finish` 再投，否则去重会看见自己），积压在后台按批排空，不用等真人再发消息。一次只折叠一批（≤ 预算的 12%），避免把十几万字符塞进一次 400 token 的摘要里。压缩失败会在本群记忆里留一条可见 note，下一轮重试。

### 6.1 对话变长会不会延迟高

改前的三个叠加来源，现在的状态：

1. **prefill 线性涨且无缓存复用** → 前缀命中率 2.1% → 81.8% → **98.5%**，稳定前缀部分不再每轮重付；每轮真正新付的只有本轮新增的记录和触发消息。
2. **前缀断点太早** → 断点从第 6 块移到转录窗口的追加处，也就是整条提示词的倒数第二个字符块。
3. **压缩在关键路径内** → 移到后台 mail，回复轮不再付双倍延迟。

仍然随群长度增长的部分：窗口本身（受字符预算封顶，默认 200K 字符），靠压缩水位线收敛；以及压缩那一轮自己付的一次摘要调用（在后台，不挡回复）。

### 6.2 为什么到不了 100%

98.5% 已经贴着物理下限了，剩下的 1.5% 拆开来是：

- **本轮新增内容**（新消息 + 我上一条回复被追加进转录，实测 45 字符）：前缀缓存的定义就是「从头开始最长匹配」，而本轮请求必须带上上一轮没有的东西，这部分天生 miss。
- **触发消息块**（实测 23 字符）：它就是本轮的任务，每轮都不同，只能排在最后。
- **提供商侧的块量化**：缓存按固定粒度命中（DeepSeek 128 token、vLLM prefix caching `block_size=16`、Anthropic 要显式 cache breakpoint），最后一个不满块永远算 miss。字符级 LCP 是乐观上界。
- **TTL**：前缀缓存有存活期（分钟级）。群里隔两小时才 @ 一次这个员工，缓存早冷了——这跟提示词怎么写无关，是群聊这种低频长间隔负载真正的天花板。
- **跨群不共享**：换一个群，公共前缀只剩 44 字符（到群名就断了），因为技能清单里带本群专属的那段。每个 (员工, 群) 是独立缓存条目，这是设计意图，不是缺陷。

所以口径应当是「**每轮只为本轮新增付 prefill**」，而不是 100%。smoke 8d 锁的就是这条：可复用前缀 ≥95%。

### 6.3 突发 / 抢占 / 接力压测（`npm run bench`）

六个场景，73 项断言，全部走真实 `scheduler.tick` + 真实 `worker.mjs` 驱动，上游是本机假 OpenAI SSE 服务（剧本可控、能记录连接被掐断的时刻）。刻意不进 `npm run qa`：里面有名次差、并发上界这类与时间耦合的断言，日常自检不必为此承担抖动。

**绝对值被本机夹具放大**：`dev/fixture-supabase.mjs` 每次写库都同步全量落盘、每次查询让出一次事件循环，单封执行 374ms 里模型侧只占约 32ms（4 片 × 8ms）。所以这张表比的是**不变量与相对量**，跨环境的绝对毫秒要接真库复测。

| 场景 | 压什么 | 实测 |
| --- | --- | --- |
| **B1** 单员工 × 8 群 × 3 封突发 | 不丢、不重、不串群、群内严格 FIFO、同（员工,群）不并发 | 预算 2：排空 3169ms、**7.6 封/秒**、峰值并发 **6**、起跑延迟（自开跑起）p50/p95 = **1245/2666ms**；预算 8：2078ms、**11.5 封/秒**、峰值 **8**、起跑延迟 **780/1437ms**，各群排空时点跨度 1441ms → **0ms** |
| **B2** 4 个并行慢任务里抢占 1 个 | 插话只掐目标群、半截正文不落群、旁观群不受扰、账目平 | 发消息 → 上游连接被掐断 max **167ms**（上游分片间隔 60ms 是下界）；发消息 → 重答落群 max **320ms**；叫停 **95ms**；没被抢占的慢任务仍跑满 5783ms；5 封原信 = 4 done + 1 cancelled，外加 2 封回执 |
| **B3** 两个员工互相 @ 接力 | hops 递增、第 3 跳触顶判负、每棒上下文承接上一棒、群里只留结论 | 3 棒 + 触顶终止端到端 **2079ms**，单棒执行 p50 **388ms**、排队 **131ms**；一条消息 @ 两个人 → 两封任务真并行（调用区间重叠）**1001ms**，单个员工 233ms |
| **B4** 权重公平：6 个 w=5 群 + 6 个 w=1 群，各积压 4 封 | 优先级落库、轻权不被饿死、争抢下仍按序落群 | 抢槽（预算 2 = 6 槽 < 12 群）：平均完成名次 **12.5 / 36.5**（无权重时都应是 24.5），重权整组先排空 **2482ms** vs 轻权 **5123ms**；富余（预算 8 = 24 槽 > 12 群）：名次差缩到 **6.0** |
| **B5** 6 路 tick 同时抢 12 封 | 认领是单行 CAS，多驱动者不能重复执行 | 重复执行 **0**，各路 `ran` 列表互不重叠，`slice_count` 全为 1，上游调用数 == 信数 |
| **B6** 崩溃留下的僵尸 running | 超 5 分钟判死、期间的插话转待办不丢、不误杀新任务 | 30 秒的 running 保留；回收为 `failed:slice_interrupted`，补投的插话 391ms 落群；被回收的僵尸本身不会执行 |

三条从这轮数据里读出来的结论：

1. **有效并发 = min(排队群数, 预算 × worker 并发轮次 3)**。预算 2 时上界 6、实测峰值 6；预算 8 而群数只有 8 时上界 8、实测 8（推导与实测吻合）。所以预算从 2 拉到 8 只买到 **1.53×**，不是 4×——预算一旦超过排队群数就是空烧，还把单封执行时间从 374ms 顶到 580ms（夹具的同步落盘被并发放大，不是调度退化）。B1 把这条写成区间断言。
2. **权重买到的是「缺槽时的优先权」，不是「永远压住别的群」**。槽位不够分时重权整组先跑完（名次差 24，满量程 48）；槽位富余时人人有槽，w=5 与 w=1 同期起跑（名次差缩到 6）。给某个群调高权重的正确预期因此是「积压时它先出」，B4 两个方向都钉住了。
3. **突发不再瞎**：P10 修完之后，8 群 × 3 封的每一群里第 k 次调用的上下文都能看到第 k−1 次的回复，落群顺序与投递顺序逐群一致。

## 8. 验收口径

- **稳定前缀** ≥ 本轮请求体的 95%（smoke 8d 已锁）；当前实测 **98.5%**。口径是「每轮只为本轮新增的记录和触发消息付 prefill」，100% 物理上做不到，原因见 6.2。
- **窗口连续性**：回复窗口第一条序号 === `covers_through_seq + 1`，中间不留既看不见也没被摘要覆盖的缺口（smoke 8c 已锁）。
- **抢占延迟** ≤ 1.5s 端到端掐断（SSE 路径实测 127ms；CLI 路径接入后同口径复测）。
- **首字延迟**不随群消息数线性增长（以 500 行群为基准回归）。
- **离线推进**：worker 在跑时，`mail.created_at → started_at` ≤ tick 间隔 + 一轮执行时间，且不依赖任何浏览器在线。
- **突发正确性**：单员工被 N 个群轰炸时不丢、不重、不串群，群内严格 FIFO；同（员工, 群）不同时跑两封（bench **B1** + smoke **8e**）。
- **有效并发** = min(排队群数, 预算 × 3)，实测峰值必须落在 [预算, 上界] 区间内；预算高于群数属于空烧（bench **B1**）。
- **权重语义**：槽位不够分时重权平均完成名次显著靠前且轻权不被饿死；槽位富余时不得断言严格优先（bench **B4** 两个方向都锁）。
- **多驱动者**：前端轮询与 worker 并行时重复执行必须为 0，`slice_count` 全为 1（bench **B5**）。
- 每轮在 `run_traces` 记 prompt 字符数与上一轮 LCP（待 R3/trace 表落地后自动采集）。
