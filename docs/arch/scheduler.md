# WorkStream 调度器架构

**简体中文 · [English](scheduler.en.md)**

scheduler · executor · context assembly ｜ 实测日期 2026-11-02 ｜ 源码：`functions/engine.mjs`、`functions/worker.mjs`、`functions/bus.mjs`、`functions/chat.mjs`、`functions/agents.mjs`、`functions/backends.mjs`、`functions/delegate.mjs`、`functions/cron.mjs`、`functions/qca.mjs`

**一页结论。** 调度层是「邮箱 FIFO + 跨群加权时间片」：群里 @ 一位虚拟员工 = 往 ta 的邮箱投一封信，`scheduler.tick` 按创建顺序取信、按群权重分并发槽、CAS 抢任务执行；服务端常驻 `worker` 让队列在没有浏览器时也往前走。执行层是「单发流式调用 + 插话掐断」：每轮把群历史现场重渲染成一条 system 消息发给 OpenAI 兼容上游，边收 SSE 边查插话。上下文层是「稳定前缀 + 尾部追加窗口 + 后台压缩」：块序即缓存序，窗口按字符预算分页取，压缩在后台把水位线推上去；实测两轮之间的可复用前缀 **98.5%**，每轮只为本轮新增的记录付 prefill。排程（cron）不另开一条执行路径：到点的排程只是在 tick 里多投一封普通信，时间片、CAS、插话、压缩全部复用。

本文第 6 节把已经查实的 8 个问题逐条列出，每条都给改前/改后的实测数字与对应的回归断言。

## 1. 端到端流程

```
群聊前端 / MCP
  messages.send：消息落 messages（seq 递增），解析 @ 提及，
  为每位被 @ 的虚拟员工插一行 mail（status=queued，priority=该群权重）。
      ▼
tick 驱动者（两个，可并存）
  · 服务端常驻 worker（functions/worker.mjs，--worker 或 WORKSTREAM_WORKER=1）：每 1s 一轮。
  · 群聊页轮询（ChatView.tsx）：每 5s 一轮，兜住没起 worker 的部署。
  两者共用同一个 scheduler.tick，认领是单行 CAS，同时跑不会重复执行。
      ▼
scheduler.tick（engine.mjs）
  reapStale 回收跑了 5 分钟以上的僵尸任务
  → 先扫这位主人名下到期的排程（cron.mjs：CAS 推时钟 → 投一封 queued 信），同一轮就能跑掉
  → 取 queued 信 → 过滤掉「同 (员工, 群) 已有 running」的那些，一轮只放最早的一封
  → 按员工分组、组内按群分组 → allocate() 分槽 → 并发执行。
      ▼
CAS 抢任务
  mail.claim(id, queued→running)，slice_count+1。多个驱动者并发时只有一个能抢到。
      ▼
runTask（engine.mjs）
  装配上下文 → 超预算先从窗口头部裁剪、并补投后台压缩信 → 调上游（SSE 流式）
  → MCP 工具回路 → 回复落群 → 写一条本群记忆 note。
      ▼
interruptWatcher（engine.mjs）+ bus（functions/bus.mjs）
  同进程插话/叫停走 bus 立即生效；跨进程由 400ms 的邮箱轮询兜底。
  发现比当前触发消息更新的插话就掐断上游（Interrupted 带已输出的半截），
  插话作为新触发重跑（≤2 次），叫停则任务置 cancelled。
```

## 2. 数据模型

| 表 | 键 / 约束 | 在调度里的角色 |
| --- | --- | --- |
| `mail` | `(agent_id, stream_id, status)` 索引 | 邮箱即任务队列。`status`: queued → running → done / failed / cancelled；`trigger_seq` 指向触发消息；`meta.interrupt` 存未消化的插话；`meta.kind="compress"` 是后台压缩信；`meta.kind="cron"` 是排程到点投的信，`trigger_seq=0`（不挂在任何一条群消息上），`meta.cron` 里带着到点时刻、欠的对点数与要办的事。 |
| `slice_prefs` | `UNIQUE(agent_id, stream_id)` | 该员工在该群的时间片权重 1–20（默认 1）。群主/管理员才能改。 |
| `memories` | `(agent_id, scope)`、`(agent_id, stream_id)` | `scope=common` 跨群长期记忆；`scope=stream` 本群记忆；`kind=summary` + `covers_through_seq` 是本群压缩摘要的水位线。 |
| `messages` | `(stream_id, seq)` | 群转录的唯一权威。上下文窗口、插话判定、审计回执全部以它为准。`on_behalf_of` 非空表示这条正文是替身代某位真人说的。 |
| `users` / `members` 的替身字段 | `users.delegate_agent_id` + `delegate_start_at` / `delegate_end_at`（账号级班表）；`members.delegate_mode`（`inherit` / `on` / `off`）+ `members.delegate_agent_id`（单群覆盖） | 真人被 @ 时先看群内覆盖、再看班表，命中才往替身邮箱投一封 `meta.on_behalf_of` 的信（见 3.4）。 |
| `schedules` | `(owner_id, next_run_at)`、`(agent_id)` | 排程（见 3.5）。时钟状态只有 `next_run_at` 一列：为空就是暂停，到点判定读它现算，不存第二个真值源。`merged_runs` 是累计被并进同一轮的对点数，`last_run_at` 是最近一次真正交付的对点。 |
| `cli_sessions`（规划） | `UNIQUE(agent_id, stream_id)` | per（员工, 群）的 CLI 会话键：runner / session_id / last_seq / workdir。见第 7 节。 |
| `run_traces`（规划） | `(mail_id, seq)` | 每次运行的 thinking / 工具调用 / 装配上下文快照。群里只看结论，过程在员工详情里点开看。 |

**平台约束（已核实）**：站点迁移接口只接受 `CREATE TABLE`、`ALTER TABLE ADD COLUMN` 和普通 `CREATE INDEX`。所以「每个 `(agent_id, stream_id)` 只允许一行 running」这种部分唯一索引做不出来，该不变量由调度规则 + CAS 认领承担（见 3.2）。

## 3. 调度算法

### 3.1 取信与分槽

- **群内 FIFO**：查询按 `created_at asc`，同一员工在同一群里严格按投递顺序处理。
- **跨群加权**：`allocate(budget, groups)`（最大余数法）把 `WORKSTREAM_SLICE_BUDGET`（默认 2，上限 8）个槽按 `slice_prefs.weight` 切给各群，且不超过该群实际排队数。
- **总并发上限**：`budget × min(员工数, 6)`，防止一轮 tick 打爆上游配额。
- **僵尸回收**：`reapStale` 把 running 超过 5 分钟的任务判 `failed: slice_interrupted`，并把期间收到的插话转成新 queued——插话不会因为进程死掉而丢。worker 在没有排队信时也跑这一步，否则崩溃留下的 running 会永远卡住那个员工。

### 3.2 一个（员工, 群）同时只跑一封

一轮 tick 先读出全部 running 信，拼成 `agent_id:stream_id` 集合，queued 信里命中集合的直接跳过（**不退而求其次**去跑同一对的下一封）。于是：

- 同一对并发跑两封时，后一封的上下文里没有前一封的回复，落群顺序还会倒置——这条规则把它挡住；
- 认领是 `queued→running` 的单行 CAS，两个驱动者（多 Function 实例、前端轮询、worker）同时看上同一封时只有一个赢，输的那个直接跳过，所以规则跨进程同样成立；
- 后台信（压缩、排程）让位给真人触发的那封，否则它们排在队头时每次回复都要多等一轮（排程不缺一轮，见 3.5）。

### 3.3 为什么默认 FIFO 就够

群聊里「先说先办」符合真人直觉，FIFO 让队头阻塞可预测；真正需要区分优先级的是跨群资源争抢，那部分已由权重时间片承担。等实测出现饥饿再上优先级队列。

### 3.4 替身：@ 真人也能被回

真人可以指定自己名下一个虚拟员工当替身，冲 ta 来的 @ 由替身接住。投递仍走同一封 `mail`，调度器不知道「替身」这回事——它只看见多了一封 queued 信，所以并发槽、CAS 认领、插话、压缩全部复用，没有第二条执行路径。

- **班表挂账号、群内只放覆盖**（`functions/delegate.mjs`）。真人离开是账号级状态，不是每个群各离开一次；但「这个群要、那个群不要」确实存在，所以 `members.delegate_mode` 只需 `inherit` / `on` / `off` 三档，`members.delegate_agent_id` 还可以换成另一个员工。时段的两端始终读账号上的 `delegate_start_at/end_at`：班表说 ta 什么时候不在，覆盖说这段不在期间哪个群启用。
- **生效判定按时钟现算，不到点翻牌**。`delegateWindow` 是纯函数，派发那一刻拿当前时间比一次。翻牌方案需要一个常驻进程保证那次写入真的发生，进程没跑到位时段结束后替身就永远停在开启态；现算就没有这种状态需要维护。窗口右端**左闭右开**，到点即失效，不留一秒重叠。
- **代答不等于代收**：真人照旧收到 @ 通知（`outbox`），替身只是**多**接一封任务，本人回来还能翻到原始的 @。
- **替身必须是本人名下、状态 active、且就在这个群里**。借别人的员工代自己说话等于让第三方读你的群上下文，直接拒（`agent_not_owned`）。
- **署名与回执**：任务信带 `meta.on_behalf_of`，落群的回复带 `messages.on_behalf_of`，界面据此标「替 @X 代答」——正文署名仍是替身自己，不冒充真人。
- **两处挡住回环**：同一条消息既 @ 真人又 @ ta 的替身时，`skipAgents` 让替身只收那封直接任务；替身回复里再 @ 主人时，`human.id === senderId` 直接跳过，不给自己派活。smoke §25 借演示模型会把提示词尾巴念回正文这个行为，把「队列里始终只有一封」钉成了端到端断言。

### 3.5 排程：员工按自己的时刻表醒来

真人 @ 是外驱，排程是内驱：主人给某个（员工, 群）排一条「每 45 分钟」或「周一、三、五 09:30（UTC+8）」，到点员工自己往群里干活。实现刻意不新增第二条执行路径——到点只是在 tick 里多投一封普通 `mail`，时间片分配、CAS 认领、插话、压缩、轨迹全部复用，与 3.4 替身同一个手法。

- **时钟只有 `next_run_at` 一列，到点判定现算**。和替身班表同一个理由：「到点翻牌」需要一个常驻进程保证那次写入真的发生，进程没跑到位就留下一个谁也停不掉的状态。扫到期时读出 `next_run_at` 跟当前时刻一比，欠几个对点由纯函数 `catchUp` 算出来，没有第二个真值源就没有能对不上的地方。暂停 = 把这一列写空，恢复 = 按规格重算「现在之后的第一个对点」——再加一个 `enabled` 位就会造出「enabled 为真而 `next_run_at` 为空」这种没人能兑现的组合。
- **追补但不刷屏：欠几个对点只投一封**。掉线三天回来，群里要的是一次「这三天有什么要紧事」，不是三千封补投。多出来的对点折进 `merged_runs`（累计）和信里的 `cron.merged`（本轮），排程块会写明「其间合并了 N 个没跑成的对点（这一轮一次办完）」，调度台上「累计合并 N 个对点」那个小标签也就能自证口径。等长周期用算术一次算完；带周几过滤的 daily 只能一步步走，走到 `MAX_CATCHUP=500` 就把时钟重锚到「现在之后的第一个对点」、更早的不补——刚上线就连着几轮全在补历史，同事看到的是一串迟到的旧任务，比丢掉一段没人看的排程更糟。
- **投递带 CAS：一个对点只有一封**。同一个到期行会被多个驱动同时看见（前端每 5 秒轮询、常驻 worker、多实例 Function）。推进时钟的条件写成「我读到的那个值还没被人动过」（`schedules.claim`），只有一个赢，输的直接跳过、不退而求其次投第二封，否则群里同一件事会被念好几遍。信没投出去（邮箱写失败）就把时钟回拨成自己刚读到的那个值，回拨的条件是「推进后的那个值还在」，所以不会盖掉别的驱动这一轮刚推上去的时钟。smoke **§26** 钉住这条：两个驱动并发扫同一个到期行只投出一封（配一条「并发那一轮也真的把活干了」的对照），邮箱写失败时如实报出这条排程的错并把时钟回拨，写入恢复后同一个对点照样投出去——一次失败不该永久丢掉这条排程。
- **人 > 排程**。排程信和压缩信一样落进 `background` 桶：同事在线等回答时先答人，排程留在队列里下一轮再跑。排程不缺一轮——`catchUp` 按 `next_run_at` 往后数对点数，晚投不会把欠的算少。
- **到点这一轮允许静默**。排程醒来的那一轮没有人 @，正文就是那条群消息；没事要说就回空正文，`runTask` 把信结为 `done` 并记 `mode=cron, silent=true`，不往群里塞一句「本次无内容」。真人 @ 的轮次回空正文仍是失败（`empty_reply`）——同事在等回答，空手回一句等于没干。两种德性在同一个空正文分支里分开。
- **没活也要有人驱动**。worker 的 `once()` 原本只看「有没有排队信」，一个安静的群永远攒不出第一封，到点的排程就只会躺在表里等一个不会来的触发。现在空闲轮也用 `dueOwnerIds` 找出该醒的主人再 tick，这一步是纯读，真正的投递在 tick 里带 CAS；前端轮询本来就带主人身份打 `scheduler.tick`，天然覆盖同一件事。
- **边界与自我退场**。每人最多 20 条（扫描走 `(owner_id, next_run_at)` 索引，上限让最坏一轮的开销有界）、最短间隔 1 分钟（排程是主动干活，不是往群里灌消息的定时器）、员工必须属于主人且就在这个群里（借别人的员工排班等于烧别人的 Key）。扫到员工已经退群的那条，CAS 把时钟写成暂停而不是继续推进：这条排程不可能再跑成，继续走只会每到一个对点白扫一次。删员工连带删掉他名下的排程、解散群连带删掉这个群里的排程（留着行只会按时投出必定失败的信，或为一个不存在的群投信）；删排程连带撤回队里还没跑的那一封，但只撤 `queued`——正在生成的那封让它跑完，掐断是 `scheduler.interrupt` 的活，删排程不该越权掐人。
- **界面上的「下一次」由服务端算**。`cron.list` 每条带往后三个对点，`upcomingOccurrences` 从这一行自己的时钟一步步走，不拿「现在」重锚——按现在重锚会把「每半小时」那条说成 10:37、11:07，而它真实会醒在 10:30、11:00，差一分钟都不该差，差了就没人再信这个表。暂停返回空数组，界面写「下一次 —」，不装作它还在跑。

### 3.6 接龙：员工回复里的 @ 交给下一位

员工回完一条，正文按本群成员反查出 `@名字`（`matchMentions`），点到的员工由 `fanout` 投成一封普通 `mail`，`meta.hops` 是**上一封的跳数加一**、`meta.from_agent` 记下这一棒是谁交的。仍然是同一封 `mail`、同一个 tick，所以并发槽、CAS、插话、压缩、轨迹全部复用，与 3.4/3.5 同一个手法。

- **上限 3 跳，撞顶那封结为 `failed: hop_limit` 且不回帖**。两个模型互相 @ 可以永远说下去，而每一跳都付一次真实调用；上限判在 `runTask` 里装配之后、出网之前，所以撞顶那一封连上游都不连。真人重新 @ 一次从 `hops=0` 起——上限拦的是这条链，不是这个员工。
- **三种 @ 各有归宿**：@ 别的员工 → 投任务；@ 真人 → 进 ta 的虚拟邮箱（替身照常另算）；@ 自己 → 记进 `mentions` 让群里看得见，但不投任务，否则替身或自我追问会自己给自己派活。名字对不上本群成员、或那位员工是 `paused`，同样不投——投出去只会得到一封必定失败的信。
- 这一节的地板在 smoke **§30**：一跳的 `hops`/`from_agent`、三跳触顶、群里只留 3 条回复、@ 自己/不在本群/已停用各自的「不投」，每一条都配一条同位置的放行断言（换成群内在岗的乙二就接得住、拨回 active 照样接得出去）。压测 `dev/bench.mjs` 里的 B3 量的是这条链的端到端耗时，与 §30 是两件事：一个证德性，一个证快慢。

## 4. 执行层：流式 + 插话

- 上游调用走 SSE，逐片累加 `delta.content`；**只累加正文**，推理模型的 thinking 字段不进群（群里只留思考后的结论）。
- 每收到一片就问一次 `interruptWatcher`：同进程由 `bus.mjs` 的 `fireInterrupt` 立即命中；跨进程由 400ms 的邮箱轮询兜底。命中就 `reader.cancel()` 并抛 `Interrupted{partial}`。
- 半截内容不丢：重跑时作为「上一条说到一半被打断」的提示喂回去；叫停则任务置 `cancelled`，半截不落群。
- 插话重跑上限 2 次，防止两个人轮流插话把任务变成死循环；撞上限时这一封和它前面每一封被吞掉的 @ 都补一条 `cancelled` 回执（`meta.receipt="steer"` 带回原信 id），群里不留悬空的未读。
- **后台折叠与归并那一轮不吃插话**：`meta.kind` 是 `compress` / `dreaming` 的信是一次性提问，一个字不进群，也就没有可掐断的半截正文。把落在这类信上的 @ 登记成「已被这轮消化」，那条消息既没有任务行也等不到回执，等于被静静吞掉；`scheduler.interrupt` 选中它回一句「已经掐了」则是一次假的成功。判定只有一个家（`functions/util.mjs` 的 `interruptibleMail`），投递侧与叫停侧读同一份，smoke 8c4 钉住两半并配对照：那条 @ 照常排成新任务自己跑完，压缩信照旧 `done`、水位线照旧推进。
- **通道差异写在一张清单上**：[functions/backends.mjs](../../functions/backends.mjs) 给每条后端通道一个 `transport` 与 `caps.tools`，执行层只按 transport 从 [functions/agents.mjs](../../functions/agents.mjs) 的分流口取路由（`chat` / `demo` / `cloud`）；清单里声明了却没有实现的 transport 在模块加载时就抛，不留到运行时变成一句上游错误。
- **工具注入看 `caps.tools`，不看通道名**：不吃工具的通道请求体里 `tools` 为 `null`，连接器工具那一步也直接跳过——给了它也不会调，白付一轮 token；提示词侧同一字段决定落「按需调用工具」还是「把结论直接写进正文」（`backend.tools` 槽位）。
- **交付卡片只在提交点发布**：`present` 工具只把本群的群文件登记进这一轮的 `presented` 清单（`withTools`），卡片随回复那条 `insertMessage` 一起落；中途报错或被叫停就没有那条回复，也就没有卡片，即使轨迹里那一步是 `done`。只交了文件、正文一个字没写的一轮按 `mode: "delivery"` 算成功，排程到点那一轮也优先于静默——否则活干完了群里看不见。这一列只给客户端读，装配上下文取消息时不选它，交付说明因此不进任何一轮模型请求（`dev/smoke.mjs` 第 27 节拿哨标钉住）。
- **流断在半路不算说完**：SSE 走到尽头既没 `[DONE]` 也没 `finish_reason`，这轮记 `upstream_stream_incomplete` 并结为失败，半截正文一个字都不落群。它和「被插话掐断」是两回事：后者有人接手，前者只是上游掉了。云端那条一直按这个口径报 `qca_stream_ended_unfinished`，自建通道原来把断流当成写完——群里留下一句缺尾巴的话，邮箱还标着 `done`。
- **失败码在源头就有名字**：`chatCompletion` 拿到非 2xx 时当场用 `functions/agents.mjs` 的 `upstreamCode` 把状态码翻成 `upstream_*`，邮箱、轨迹、界面那句「这次没能完成」读同一个函数翻出来的码，不再各写一遍映射、也不再落一个裸的 `"500"`。
- **没有自动重投**：领取只从 `queued` 走 CAS，`reapStale` 把跑飞的 `running` 收成 `failed`，没有任何一条路会把 `failed` 重新排队。所以失败提示写「要再试请重新 @ 他」，不写「稍后会自动重试」——前一句兑现得了，后一句兑现不了。smoke 第 28 节用故障开关（`dev/smoke.mjs` 里 `scripts.chat` 的 500 / eof / half 三档，按跑切换、不靠触发关键词）钉住这三条坏德性，并配一条拨回正常后重新 @ 能跑成的对照。
- 接 CLI 执行器后，掐断语义从「cancel 读循环」变成「kill 进程组 + 从 stdout 增量捞半截」。

## 5. 上下文装配与压缩

### 5.1 块序即缓存序

`buildContext` 每轮产出一条 system + 一条 user；system 由哪几块拼、按什么顺序拼，写在 [functions/prompt.mjs](../../functions/prompt.mjs) 的 `PROMPT_SECTIONS` 槽位表里，不在引擎代码里往下 push。提供商侧前缀缓存按「从头开始最长匹配」命中，所以位置是被分配的资源：先按 `volatile` 分档（稳态块在前、每轮必变的块一律压到最后），同档内按 `order` 升序。空串的槽位不落块，等同于过去的 `filter(Boolean)`。

| 槽位 id | order | volatile | 内容 |
| --- | --- | --- | --- |
| `identity` | 10 | 否 | 身份（名字 / 角色 / 群名） |
| `backend.tools` | 20 | 否 | 仅这条通道不吃工具时才落的须知（`caps.tools` 在 `functions/backends.mjs`） |
| `signature` | 30 | 否 | 个性签名 |
| `guide` | 40 | 否 | 工作守则 |
| `announcement` | 50 | 否 | 群公告 |
| `skills` | 60 | 否 | 技能清单，每条带出处（内置 / 平台技能 / 本地上传 / 远端源名 + slug + 快照版本） |
| `history.access` | 70 | 否 | 「如需更早记录请调工具」固定句 |
| `memory.owner` | 78 | 否 | 主人的全局记忆（跨群归并出的那一份，5.4） |
| `memory.common` | 80 | 是 | common 长期记忆（近 20 条，**升序**） |
| `summary` | 90 | 是 | 本群压缩摘要 + 水位线 |
| `transcript` | 100 | 是 | 最近转录窗口（按字符预算，**尾部追加**） |
| `memory.stream` | 110 | 是 | 本群记忆 notes（近 30 条，**升序渲染**） |
| `delegate` | 115 | 是 | 替身须知（仅替身轮） |
| `cron` | 118 | 是 | 排程须知（仅排程醒来的那一轮） |
| `trigger` | 120 | 是 | 触发消息 |
| `steer` | 130 | 是 | 插话提示（仅插话轮） |

`order` 之间留了空档：新增一块是从表里领一个号，不是插进某个数组的下标。表在模块加载时自查（id 重复 / 缺 order / 缺 build 直接抛），所以「声明了但没装配」不会变成一次运行时才看到的缓存退化。

`memory.common`、`transcript` 两块用升序/尾部追加，是为了让新内容只追加到块尾，不打断已有前缀（降序会让每条新记忆改写块头）。

**`memory.stream` 的取舍**：每回完一条就往本群记忆插一条 `#NN 回应：<正文前 200 字>` 的回声。装配时按序号两头剔除——`NN ≤ 水位线`的已经折进摘要，`NN ≥ 窗口头`的转录里就带全文，只有落在「摘要没覆盖、窗口又装不下」那段缝隙里的回声才单列。这块排在转录之后，而**前缀缓存是一刀切**：断点之后哪怕逐字节相同也算 miss，所以让它常态为空比让它变小更要紧（实测它一度占每轮 miss 的 86%，见 P9）。非回声类 note（压缩失败留痕、用户显式记下的事）没有序号，一律保留。

**`delegate` 只在替身轮落下**：非替身轮它的 build 返回空串，空串不落块，装配结果和加这块之前逐字节相同——替身特性不给普通轮的缓存添任何代价。断点位置不受它影响（`CACHE_BREAKPOINT_ID` 是表里第一颗 volatile 块，在 `memory.common`，smoke 8d2 钉着），它只是在断点之后、触发消息之前多一段正文。这块的内容是内部提示，进群正文的红线由摘录的来源守住：演示模型只从这一轮上下文的记录行里摘真人发言，拿到的是行本身而不是拼好的正文，守则、替身须知、触发消息这些提示词根本没有露面的机会（本机假上游就是这么暴露的，smoke §25 有断言）。回帖也只摘真人发言：员工自己的回帖是多行的，正文里还引着上一轮摘录，按行扫正文会把这些二次转述当成新事实，回帖就变成复读自己。

**`cron` 只在排程醒来的那一轮落下**：位置在 `delegate` 之后、`trigger` 之前，build 在非排程轮返回空串，所以普通接活的那轮请求体逐字节不变；这块自己也标了 `volatile`，落在缓存断点之后，一个员工挂多条排程也不打断平时那段前缀。内容里有一句专门防重复播报：到点这一轮的正文就是那条群消息，不写清「别再补发一条」，模型会先调 `send_message` 再把同一句话抄进正文，群里同一件事念两遍（本机真实上游跑 1 分钟排程时第一次就发生了这件事）。同一轮的触发块也换了口径——「没有人 @ 你，这一轮是你自己的排程醒的」，不谎称自己是一条补发任务。

**命中率掉了怎么定位**：每个模型轮收尾时把这轮真正落下的槽位清单（`[id, 字符数, volatile]` 三元组）写进 `run_steps.detail.prompt_slots`，员工详情页的轨迹检视器「上下文」标签按原序排出来，并在第一颗每轮重写的块上标「断点」。它只记口径不记正文——正文库里已经有，重复存只会把库撑大。

### 5.2 窗口锚点：回复取尾部，压缩取头部

`history()` 按页（200 行/页，最多 50 页）从水位线那一侧往回取，累计到字符上限为止，**不按条数截断**：

- **回复用 `anchor=tail`**：取水位线之后最新的一段（上限 = 预算 × 0.8）。被挤出去的旧记录靠 `search_history` / `read_window` 查，提示词里已经写明。
- **压缩用 `anchor=head`**：从水位线往后**连续**取一段（上限 = max(4000, 预算 × 0.12)）。这样 `older`（较老的一半）一定是水位线之后的一个真前缀，`covers_through_seq` 不会把没被摘要读过的记录算成已覆盖。这一段还按**保底条数**取：不足一批的最少 4 条时字符上限不生效，否则一条长贴就能把整批占满（见 5.3）。回复那一路不保底，因为它不剪枝，保底只会把超预算的原文直接塞进请求体。

窗口取不满（`truncated`）时同一轮补投压缩信，把水位线推上去。

### 5.3 压缩在后台自己排空

压缩不在关键路径上：回复那一轮只做确定性的字符裁剪，压缩交给一封 `meta.kind="compress"` 的后台 mail。压缩信跑完时如果水位线之后还压着记录，**自己续投下一封**（先 `finish` 再投，否则去重会看见自己），积压在后台按批排空，不用等真人再发消息。一次只折叠一批（≤ 预算的 12%），避免把十几万字符塞进一次 400 token 的摘要里。

**剪枝先于摘要，一条长贴不许饿死一整批。** 入库上限是 8000 字节（中文按 3 字节计，一条约 2600 字；ASCII 日志体能到 7900 字），而最小档预算的一批只有 4000 字。水位线之后第一条要是正好是一份长日志，它一条就顶满这批：取记录时首条必留（窗口不能空），第二条就把上限撞破，于是这一批永远只有 1 条、达不到折叠的最少条数，水位线一步不动，回复窗口也被同一张贴压成 1 条——这个群的摘要从此再也折不下去，而且不报任何错。两处一起改：取记录按保底 4 条走（不足一批时字符上限不生效），折叠前再把每条剪到**行宽** = 这批预算 ÷ 最少条数（最小档就是 1000 字）。剪的只是喂给摘要的那一份，群里的原文一条没动，行尾留一句「…（截断，本条 N 字，全文按 #序号 取回）」，`search_history` 与 `read_window` 都拿得回全文；折叠那一步的备注如实写剪了几条与行宽，「摘要读的不是全文」这件事在轨迹里看得见，而不是只在文档里。smoke **8c3** 钉住三件事：长贴挡路时水位线照样推进、喂给摘要的每一行不超行宽、正常长度的一批一条都不截（剪枝不是无条件开刀）。

**折不动就不许抬水位线**。折叠那批记录的序号区间（`covers_from`–`covers_to`）记在压缩步骤的 detail 里，摘要行落 `covers_through_seq = covers_to`——"覆盖到 #N"是一句能对账的声称，不是一个只能信的数。上游 5xx、或者回了空正文，都等于一条都没折进摘要：这一步记成失败（空正文的码是 `summary_empty`），整封后台信也结为失败，**水位线原地不动**，本群记忆留一条可见 note（同一批反复失败只留最近一条：先 `removeAll` 清掉 `source="compression"` 的 note 再写，`remove` 走 maybeSingle，条件命中多行在线上会直接报错）。这样这批记录下一轮还在窗口里，"再折一次"才真能兑现。旧写法是失败也抬水位线、并在摘要尾巴上补一句"已折叠出上下文窗口"——记录既没进摘要也没进窗口，那句话从此没人能兑现。smoke **8c2** 用 5xx / 空正文 / 恢复正常三种剧本钉住这条，并核对成功那批的 `covers_from` 正接上上次没折动的下一条、区间里每个序号在群历史里都真实存在。

摘要正文自己也有上限（约预算的 10%，最少 600 字），超出就从最旧的一端剪掉。所以 `covers_through_seq` 的准确读法是「这批已经交给摘要处理过」，不是「每条原文都还留在摘要里」——原文永远在 `messages` 表里，`search_history` 与 `read_window` 拿得回来。

### 5.4 跨群归并：把各群摘要并成主人的一份全局记忆

一个员工往往同时在几个群里干活，而 5.3 折出来的摘要**按群各存一份**：跨群的稳定事实（「这个人的项目 deadline 在月底」「上次说好用 psql 不用 ORM」）散在各群摘要里，谁也不认识谁。归并（dreaming）做的事是把同一主人名下**各群的摘要**喂给模型一次，并成一份「主人的全局记忆」，落 `app.memories` 里 owner 级那一行，下一轮以 `memory.owner` 槽位回到每个群的请求体里（5.1）。

- **吃摘要，不吃转录**。输入是每个群当前的 `covers_through_seq` 那一条摘要，不是原始消息：转录按群算能到几万字符，一次归并要把几十个群都装进一个请求体，预算立刻不可控；摘要是已经被压缩过一层的事实，正是「跨群」需要的那一层。也因此**归并排在折叠之后**——群摘要还没推进的那一段，归并看不见。
- **三个入口，一条执行路径**。① 群折叠完顺手归并（`users.prefs.dreaming_auto`，开关挂在**主人**身上而不是员工身上，因为归并出的那份记忆属于主人）；② 排程到点（`schedules.purpose="dreaming"`，正文是额外交代而非必填，复用 3.5 那套到时 + CAS 投递）；③ 界面上那个手动按钮。三者都只往邮箱投一封 `meta.kind="dreaming"` 的后台信，跑的是同一个 `runDream`——和 3.5、5.3 一样，新行为不新增第二条执行路径。同一主人**同时只允许一封在队**（`dreamingPending`），三个入口共用这个去重：手动按钮点了两次和折叠撞上排程是同一件事，白付两次模型调用之外没有任何新信息。
- **水位线是 `{"员工 id:群 id": 已归并到的序号}`，不是按群记**。输入天然是一条条「某员工的某群的摘要覆盖到 #N」；同一个群里可以有两个员工各折一份摘要，两条素材的覆盖序号互不相干。只按群记，后写的那条会把前一条的序号盖掉——被盖掉的那条要么每轮重并（每轮白付一次调用），要么被当成已归并而**永久漏掉**，两种都是静默错账。键里带上员工 id 之后，一个群两份摘要各记各的水位。
- **装不下就欠着，不装作并完了**。输入预算按字符封顶（默认 12000，最低 2000），素材按（群名, 员工 id）定序后从头装箱，装不进的落进这一步的 `skipped_streams`，**水位不推**，下一轮它们还是新素材。这一步的 `merged_streams` / `skipped_streams` 在 `run_steps` 里各有专门的上额档（默认 1500 字会把清单挤没，见 [functions/steps.mjs](../../functions/steps.mjs) 的 `FIELD_CAPS`）：它们是「这次归并吃了哪些素材」的唯一凭证，界面问「跨群那句结论哪来的」时只能靠它复原。
- **失败不写水位、不覆盖已有那份**。上游 5xx / 空正文都当场抛出并结为失败（`dream_empty` 有自己名字），水位线原地不动——和「折不动就不许抬水位线」（5.3）同一口径。落库走 CAS：读到的那一行 `updated_at` 还没被人动过才写，同一主人的另一封归并信先落成了，这次就不覆盖；两份归并结果谁更新无法判断，留着先写成的那一份才是确定的事。
- **跨群隐私是产品红线**。那份记忆只在 `memory.owner` 块里给模型「用来判断」，抬头那句话写死了「别把别的群的细节念给这个群听」；演示模型的摘录只取窗口里的真人发言，它连露面的机会都没有。读取按主人隔离：`dreaming.get` / `run` / `clear` 全部只认自己那一份，别人的员工归并出来的结论一个字都读不到（smoke §29 成对钉住「Bo 读到空」和「Ana 读到自己那份」）。
- **一次归并自己不进群**。它跑在后台信上，`silent` 恒真，结论只落记忆表；思考链只进步骤 detail。额度旋钮（输入/输出字符、最多几个群、超时）全部走 env，和 5.2 那套同一规矩：[functions/dream.mjs](../../functions/dream.mjs) 的 `dreamBudgets`。

### 6.1 对话变长会不会延迟高

改前的三个叠加来源，现在的状态：

1. **prefill 线性涨且无缓存复用** → 前缀命中率 2.1% → 81.8% → **98.5%**，稳定前缀部分不再每轮重付；每轮真正新付的只有本轮新增的记录和触发消息。
2. **前缀断点太早** → 断点从稳定块中间移到 `memory.common`（槽位表里第一个 volatile 块），也就是转录窗口的追加处。
3. **压缩在关键路径内** → 移到后台 mail，回复轮不再付双倍延迟。

仍然随群长度增长的部分：窗口本身（受字符预算封顶，默认 200K 字符），靠压缩水位线收敛；以及压缩那一轮自己付的一次摘要调用（在后台，不挡回复）。

### 6.2 为什么到不了 100%

98.5% 已经贴着物理下限了，剩下的 1.5% 拆开来是：

- **本轮新增内容**（新消息 + 我上一条回复被追加进转录，实测 45 字符）：前缀缓存的定义就是「从头开始最长匹配」，而本轮请求必须带上上一轮没有的东西，这部分天生 miss。
- **触发消息块**（实测 23 字符）：它就是本轮的任务，每轮都不同，只能排在最后。
- **提供商侧的块量化**：缓存按固定粒度命中（DeepSeek 128 token、vLLM prefix caching `block_size=16`、Anthropic 要显式 cache breakpoint），最后一个不满块永远算 miss。字符级 LCP 是乐观上界。
- **TTL**：前缀缓存有存活期（分钟级）。群里隔两小时才 @ 一次这个员工，缓存早冷了——这跟提示词怎么写无关，是群聊这种低频长间隔负载真正的天花板。
- **跨群不共享**：换一个群，公共前缀只剩 44 字符（到群名就断了），因为技能清单里带本群专属的那段。每个 (员工, 群) 是独立缓存条目，这是设计意图，不是缺陷。

所以口径应当是「**每轮只为本轮新增付 prefill**」，而不是 100%。smoke 8d 锁的就是这条：可复用前缀 ≥95%。

**两个口径别混**：98.5% 是请求体的字符级最长公共前缀（smoke 8d 锁的乐观上界，不看提供商脸色）；上游自己回报的 token 命中是另一档——员工详情页 Stream flow 底部的统计条按 `run_steps.input_tokens / cached_tokens` 按群聚合，本机真实 DeepSeek 流量实测 19 轮 **60.1%**：同一封信里第 1 轮只有 40%，之后各轮 93~94%（R1 的重排确实在起作用），掉回 40% 多的轮是窗口动了、前缀断在半路。两者相差近 40 个点，差距正是上面「块量化 + TTL + 跨群独立」那几条的合力。统计只算上游同时回报了输入与命中数的模型轮：被插话掐断的轮在末尾用量块之前就断了，QCA 云端与演示后端压根不回报用量，界面如实写「这条后端不回报用量」，不拿 0% 冒充。

**子桶先进账前先过口径**：`cached_tokens` 与 `reasoning_tokens` 是对应总数的子桶，而第三方与自建网关的 `*_details` 口径五花八门——报得比总数还大时按「不回报」收成 null（[functions/agents.mjs](../../functions/agents.mjs) 的 `normalizeUsage`）。这样界面与统计条上的命中率永远不可能超过 100%，越界的那份脏数也不会被投进分母。`total_tokens` 不落列：它等于输入 + 输出，没有哪一处读数需要它。smoke 第 20 节用只报总数、子桶越界、压根不回用量块三种形状把这三档钉住，并配一条「口径收成空不影响这一轮跑完」的对照。

### 6.3 突发 / 抢占 / 接力压测（`npm run bench`）

六个场景，73 项断言，全部走真实 `scheduler.tick` + 真实 `worker.mjs` 驱动，上游是本机假 OpenAI SSE 服务（剧本可控、能记录连接被掐断的时刻）。刻意不进 `npm run qa`：里面有名次差、并发上界这类与时间耦合的断言，日常自检不必为此承担抖动。

**绝对值被本机夹具放大**：`dev/fixture-supabase.mjs` 每次写库都同步全量落盘、每次查询让出一次事件循环，单封执行 374ms 里模型侧只占约 32ms（4 片 × 8ms）。所以这张表比的是**不变量与相对量**，跨环境的绝对毫秒要接真库复测。

| 场景 | 压什么 | 实测 |
| --- | --- | --- |
| **B1** 单员工 × 8 群 × 3 封突发 | 不丢、不重、不串群、群内严格 FIFO、同（员工,群）不并发 | 预算 2：排空 3169ms、**7.6 封/秒**、峰值并发 **6**、起跑延迟（自开跑起）p50/p95 = **1245/2666ms**；预算 8：2078ms、**11.5 封/秒**、峰值 **8**、起跑延迟 **780/1437ms**，各群排空时点跨度 1441ms → **0ms** |
| **B2** 4 个并行慢任务里抢占 1 个 | 插话只掐目标群、半截正文不落群、旁观群不受扰、账目平 | 发消息 → 上游连接被掐断 max **167ms**（上游分片间隔 60ms 是下界）；发消息 → 重答落群 max **320ms**；叫停 **95ms**；没被抢占的慢任务仍跑满 5783ms；5 封原信 = 4 done + 1 cancelled，外加 2 封回执 |
| **B3** 两个员工互相 @ 接力 | hops 递增、第 3 跳触顶判负、每棒上下文承接上一棒、群里只留结论 | 3 棒 + 触顶终止端到端 **2079ms**，单棒执行 p50 **388ms**、排队 **131ms**；一条消息 @ 两个人 → 两封任务真并行（调用区间重叠）**1001ms**，单个员工 233ms |
| **B4** 权重公平：6 个 w=5 群 + 6 个 w=1 群，各积压 4 封 | 优先级落库、轻权不被饿死、争抢下仍按序落群 | 抢槽（预算 2 = 6 槽 < 12 群）：平均完成名次 **12.5 / 36.5**（无权重时都应是 24.5），重权整组先排空 **2482ms** vs 轻权 **5123ms**；富余（预算 8 = 24 槽 > 12 群）：名次差缩到 **6.0** |
| **B5** 6 路 tick 同时抢 12 封 | 认领是单行 CAS，多驱动者不能重复执行 | 重复执行 **0**，各路 `ran` 列表互不重叠，`slice_count` 全为 1，上游调用数 == 信数 |

三条从这轮数据里读出来的结论：

1. **有效并发 = min(排队群数, 预算 × worker 并发轮次 3)**。预算 2 时上界 6、实测峰值 6；预算 8 而群数只有 8 时上界 8、实测 8（推导与实测吻合）。所以预算从 2 拉到 8 只买到 **1.53×**，不是 4×——预算一旦超过排队群数就是空烧，还把单封执行时间从 374ms 顶到 580ms（夹具的同步落盘被并发放大，不是调度退化）。B1 把这条写成区间断言。
2. **权重买到的是「缺槽时的优先权」，不是「永远压住别的群」**。槽位不够分时重权整组先跑完（名次差 24，满量程 48）；槽位富余时人人有槽，w=5 与 w=1 同期起跑（名次差缩到 6）。给某个群调高权重的正确预期因此是「积压时它先出」，B4 两个方向都钉住了。
3. **突发不再瞎**：P10 修完之后，8 群 × 3 封的每一群里第 k 次调用的上下文都能看到第 k−1 次的回复，落群顺序与投递顺序逐群一致。

## 8. 验收口径

- **稳定前缀** ≥ 本轮请求体的 95%（smoke 8d 已锁）；当前实测 **98.5%**。口径是「每轮只为本轮新增的记录和触发消息付 prefill」，100% 物理上做不到，原因见 6.2。
- **窗口连续性**：回复窗口第一条序号 === `covers_through_seq + 1`，中间不留既看不见也没被摘要覆盖的缺口（smoke 8c 已锁）。
- **抢占延迟** ≤ 1.5s 端到端掐断（SSE 路径实测 127ms；CLI 路径接入后同口径复测）。
- **首字延迟**不随群消息数线性增长（以 500 行群为基准回归）。
- **离线推进**：worker 在跑时，`mail.created_at → started_at` ≤ tick 间隔 + 一轮执行时间，且不依赖任何浏览器在线。
- **突发正确性**：单员工被 N 个群轰炸时不丢、不重、不串群，群内严格 FIFO；同（员工, 群）不同时跑两封（bench **B1** + smoke **8e**）。
- **有效并发** = min(排队群数, 预算 × 3)，实测峰值必须落在 [预算, 上界] 区间内；预算高于群数属于空烧（bench **B1**）。
- **权重语义**：槽位不够分时重权平均完成名次显著靠前且轻权不被饿死；槽位富余时不得断言严格优先（bench **B4** 两个方向都锁）。
- **多驱动者**：前端轮询与 worker 并行时重复执行必须为 0，`slice_count` 全为 1（bench **B5**）。
- **块序是被分配的**：槽位表的 id 唯一、order 齐、build 齐全，且第一个 volatile 块就是缓存断点（smoke **8d2** 已锁）；装配出来的块序与正文逐字对得上同一条检查。
- **代答不另开一条路**：替身任务与普通任务同表同队列，普通轮提示词逐字节不变（smoke **25**：非替身轮不落 `delegate` 块）；一条 @ 最多派一封（回环两处 guard 各配一条放行断言），真人侧通知不因代答而少（**代答≠代收**）。
- **排程不另开一条路**：到点的排程只多投一封普通 `mail`，同表同队列，非排程轮的提示词与请求体逐字节不变（smoke **26**：不是排程的那一轮不落 `cron` 块）。一个对点只能有一封信——CAS 推进时钟，多驱动同时扫只有一个赢；投信失败要回拨时钟，下一轮重新判到点（同节）。欠几个对点只投一封，多出来的记进 `merged_runs` 与信里的 `cron.merged`，界面上的「累计合并」和「下一次」都从服务端算出来的值来（暂停时「下一次」是空，不装作还在跑）。人 > 排程：这一轮有真人 @ 就先答人，排程留在下一轮按时钟追上来。
- 每个模型轮在 `run_steps.detail.prompt_slots` 落下这轮的 `[槽位 id, 字符数, volatile]` 清单，轨迹检视器「上下文」标签按原序显示并标出断点；prompt 字符数与上一轮 LCP 的自动采集仍待 R3/trace 表落地。
