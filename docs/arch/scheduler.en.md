# WorkStream Scheduler Architecture

**English** · [简体中文](scheduler.md)

scheduler · executor · context assembly | measured on 2026-11-02 | source: `functions/engine.mjs`, `functions/worker.mjs`, `functions/bus.mjs`, `functions/chat.mjs`, `functions/agents.mjs`, `functions/backends.mjs`, `functions/delegate.mjs`, `functions/cron.mjs`, `functions/qca.mjs`

**One-page conclusion.** The scheduling layer is a "virtual inbox FIFO + cross-stream weighted time slices": @-mentioning a virtual employee in a stream = delivering one mail into that employee's inbox; `scheduler.tick` takes mails in creation order, splits concurrency slots by stream weight, and claims tasks with a CAS compare-and-write before executing them; the resident server-side `worker` keeps the queue moving even when no browser is open. The execution layer is a "single streaming call + interrupt cut-off": each round the stream history is re-rendered on the spot into one system message sent to the OpenAI-compatible upstream, and interrupts are checked while the SSE chunks arrive. The context layer is a "stable prefix + window appended at the tail + background compaction": block order is cache order, the window is paged out by character budget, and compaction pushes the watermark up in the background; the measured reusable prefix between two rounds is **98.5%**, so each round only pays prefill for the records this round added. Schedules (cron) do not open a second execution path: a schedule at its due tick just delivers one more ordinary mail inside the tick, and time slices, CAS, interrupts and compaction are all reused.

Section 6 of this document lists, one by one, the 8 issues that have been verified, each with measured before/after numbers and the corresponding regression assertion.

## 1. End-to-end flow

```
Group chat frontend / MCP
  messages.send: the message lands in messages (seq increments), @-mentions are parsed,
  and one mail row is inserted for each @-mentioned virtual employee (status=queued, priority=that stream's weight).
      ▼
tick drivers (two of them, may coexist)
  · Resident server-side worker (functions/worker.mjs, --worker or WORKSTREAM_WORKER=1): one round every 1s.
  · Group chat page polling (ChatView.tsx): one round every 5s, covering deployments where no worker was started.
  Both share the same scheduler.tick; claiming is a single-row CAS, so running both at once never executes twice.
      ▼
scheduler.tick (engine.mjs)
  reapStale collects zombie tasks that have been running for more than 5 minutes
  → first scans the schedules due under this owner (cron.mjs: CAS pushes the clock → delivers one queued mail), so it can run in the same round
  → takes queued mails → filters out those whose (employee, stream) pair already has a running one; a round releases only the oldest per pair
  → groups by employee, within a group by stream → allocate() assigns slots → executes concurrently.
      ▼
CAS claim
  mail.claim(id, queued→running), slice_count+1. When several drivers race, exactly one wins the task.
      ▼
runTask (engine.mjs)
  assemble the context → over budget, trim from the window head first and re-deliver a background compaction mail → call the upstream (SSE streaming)
  → MCP tool loop → the reply lands in the stream → write one note into this stream's memory.
      ▼
interruptWatcher (engine.mjs) + bus (functions/bus.mjs)
  Same-process interjections and stops go through bus and take effect at once; across processes a 400ms inbox poll covers them.
  An interjection newer than the current trigger message cuts the upstream off (Interrupted carries the half already emitted),
  the interjection reruns as a new trigger (≤2 times), and a stop sets the task to cancelled.
```

## 2. Data model

| Table | Keys / constraints | Role in scheduling |
| --- | --- | --- |
| `mail` | `(agent_id, stream_id, status)` index | The inbox is the task queue. `status`: queued → running → done / failed / cancelled; `trigger_seq` points at the triggering message; `meta.interrupt` holds undigested interrupts; `meta.kind="compress"` is a background compaction mail; `meta.kind="cron"` is the mail delivered when a schedule reaches its due tick, with `trigger_seq=0` (not hung on any stream message), and `meta.cron` carries the due-tick time, the number of due ticks owed and the work to do. |
| `slice_prefs` | `UNIQUE(agent_id, stream_id)` | The time-slice weight 1-20 (default 1) of that employee in that stream. Only the stream owner/admin may change it. |
| `memories` | `(agent_id, scope)`, `(agent_id, stream_id)` | `scope=common` is cross-stream long-term memory; `scope=stream` is this stream's memory; `kind=summary` + `covers_through_seq` is this stream's compaction-summary watermark. |
| `messages` | `(stream_id, seq)` | The single authority for the stream transcript. The context window, the interrupt determination and audit receipts all take it as the source of truth. A non-empty `on_behalf_of` means this body was spoken by a delegate on behalf of a certain human. |
| The delegate fields on `users` / `members` | `users.delegate_agent_id` + `delegate_start_at` / `delegate_end_at` (the account-level roster); `members.delegate_mode` (`inherit` / `on` / `off`) + `members.delegate_agent_id` (the per-stream override) | When a human is @-mentioned, the per-stream override is checked first, then the roster; only on a hit does the delegate's virtual inbox get one mail carrying `meta.on_behalf_of` (see 3.4). |
| `schedules` | `(owner_id, next_run_at)`, `(agent_id)` | Schedules (see 3.5). The clock state is the single `next_run_at` column: empty means paused, the due check reads it and computes on the spot, no second source of truth is stored. `merged_runs` is the cumulative number of due ticks merged into the same round, `last_run_at` is the most recent due tick actually delivered. |
| `cli_sessions` (planned) | `UNIQUE(agent_id, stream_id)` | The per (employee, stream) CLI session key: runner / session_id / last_seq / workdir. See section 7. |
| `run_traces` (planned) | `(mail_id, seq)` | A snapshot of thinking / tool calls / assembled context for each run. The stream only shows the conclusion; the process is expanded in the employee detail view. |

**Platform constraint (verified)**: the site migration API only accepts `CREATE TABLE`, `ALTER TABLE ADD COLUMN` and plain `CREATE INDEX`. So a partial unique index like "only one running row allowed per `(agent_id, stream_id)`" cannot be built, and that invariant is carried by the scheduling rules + the CAS claim (see 3.2).

## 3. Scheduling algorithm

### 3.1 Taking mail and allocating slots

- **FIFO within a stream**: the query is ordered by `created_at asc`, so the same employee in the same stream processes strictly in delivery order.
- **Weighted across streams**: `allocate(budget, groups)` (largest-remainder method) splits the `WORKSTREAM_SLICE_BUDGET` (default 2, cap 8) slots across streams according to `slice_prefs.weight`, and never beyond the number that stream actually has queued.
- **Total concurrency cap**: `budget × min(#employees, 6)`, so one tick round cannot blow the upstream quota.
- **Zombie reclaim**: `reapStale` judges running tasks older than 5 minutes as `failed: slice_interrupted` and turns the interrupts received in the meantime into new queued mail -- an interrupt is never lost because the process died. The worker runs this step even when no mail is queued, otherwise a running row left behind by a crash would block that employee forever.

### 3.2 One (employee, stream) runs at most one mail at a time

A tick round first reads all running mail and builds a set of `agent_id:stream_id` keys; queued mail whose key hits the set is skipped outright (it does **not settle for the next-best**, running the next mail of the same pair). As a result:

- If two mails of the same pair ran concurrently, the second one's context would not contain the first one's reply and the order they land in the stream would be inverted -- this rule blocks that;
- The claim is a single-row CAS `queued→running`; when two drivers (multiple Function instances, frontend polling, the worker) eye the same mail at once, only one wins and the loser skips it, so the rule holds across processes just the same;
- Background mail (compaction, schedules) yields to the mail triggered by a human, otherwise, whenever they sit at the head of the queue, every reply would have to wait one extra round (a schedule never loses a round, see 3.5).

### 3.3 Why plain FIFO is enough by default

In a stream, "first said, first served" matches human intuition, and FIFO makes head-of-line blocking predictable; what actually needs priority differentiation is cross-stream resource contention, and that part is already carried by the weighted time slices. A priority queue comes only once starvation shows up in measurements.

### 3.4 Delegate: a @ at a human can also get answered

A human can designate one of the virtual employees under them as their delegate, and @-mentions aimed at that human are caught by the delegate. Delivery still goes through the same `mail`; the scheduler knows nothing about "delegates" -- it only sees one more queued mail, so concurrency slots, CAS claims, interrupts and compaction are all reused and there is no second execution path.

- **The roster hangs on the account, the stream only holds the override** (`functions/delegate.mjs`). A human being away is account-level state, not "away once per stream"; but "wanted in this stream, not in that one" really exists, so `members.delegate_mode` needs only the three values `inherit` / `on` / `off`, and `members.delegate_agent_id` can additionally swap in a different employee. Both ends of the time window are always read from the account's `delegate_start_at/end_at`: the roster says when the person is away, the override says which streams are enabled during that absence.
- **The activation check is computed against the clock; nothing gets flipped at the deadline**. `delegateWindow` is a pure function, compared once against the current time at the moment of dispatch. A flip-the-switch scheme would need a resident process to guarantee that write actually happens; if the process is not running when the window ends, the delegate stays stuck in the enabled state forever. Computing on the spot means there is no such state to maintain. The right end of the window is **left-closed, right-open**: it expires at the tick, with not one second of overlap.
- **Answering on behalf is not receiving on behalf**: the human still gets the @ notification as before (`outbox`); the delegate only catches one **extra** task mail, so when the person is back they can still find the original @.
- **The delegate must be an employee under that same person, in status active, and in this very stream**. Borrowing someone else's employee to speak for you amounts to letting a third party read your stream context, so it is rejected outright (`agent_not_owned`).
- **Signature and receipt**: the task mail carries `meta.on_behalf_of`, the reply that lands in the stream carries `messages.on_behalf_of`, and the UI marks it "answered on behalf of @X" accordingly -- the signature in the body is still the delegate's own; it does not impersonate the human.
- **Two places block the loop**: when the same message @-mentions both the human and their delegate, `skipAgents` makes the delegate receive only that one direct task mail; when the delegate's reply @-mentions its owner, `human.id === senderId` skips it outright, so no work is assigned to oneself. smoke §25 borrows the demo model's behavior of reading the prompt tail back into the body and pins "there is always exactly one mail in the queue" as an end-to-end assertion.

### 3.5 Schedules: employees wake up on their own timetable

A human's @ is external drive; a schedule is internal drive: the owner gives a certain (employee, stream) a schedule such as "every 45 minutes" or "Mon, Wed, Fri 09:30 (UTC+8)", and at the due tick the employee goes and does proactive work in the stream on its own. The implementation deliberately adds no second execution path -- coming due just delivers one more ordinary `mail` inside the tick, and time-slice allocation, CAS claims, interrupts, compaction and trajectories are all reused, the same technique as the 3.4 delegate.

- **The clock is the single `next_run_at` column; the due check is computed on the spot**. The same reason as the delegate roster: "flip the switch when it comes due" would need a resident process to guarantee that write actually happens, and if the process is not running it leaves behind a state nobody can stop. When scanning for due items, `next_run_at` is read and compared against the current moment, and the number of due ticks owed is computed by the pure function `catchUp` -- with no second source of truth there is nothing that can fail to line up. Pause = write this column empty, resume = recompute "the first due tick after now" from the spec; adding an `enabled` bit would create combinations like "enabled is true but `next_run_at` is empty" that nobody can ever honor.
- **Catch-up, but no spam: however many due ticks are owed, only one mail is delivered**. Back online after three days away, what the stream wants is one "what mattered over these three days", not three thousand backfilled deliveries. The extra due ticks are folded into `merged_runs` (cumulative) and into `cron.merged` in the mail (this round), and the schedule block spells out "N due ticks that could not run were merged in the meantime (all handled in this one round)" -- which is also how the "N due ticks merged in total" chip on the schedule console proves its own scope. Equal-length periods are computed in one arithmetic pass; a daily with a weekday filter can only step forward one tick at a time, and once it reaches `MAX_CATCHUP=500` the clock is re-anchored to "the first due tick after now" and anything older is not caught up -- right after launch, spending several rounds in a row replaying history would show colleagues a string of late old tasks, which is worse than losing a stretch of a schedule nobody was watching.
- **Delivery carries a CAS: one due tick, one mail**. The same due row is seen by multiple drivers at once (the frontend polling every 5 seconds, the resident worker, multi-instance Functions). The clock-advance condition is written as "the value I read has not been touched by anyone else" (`schedules.claim`); only one wins, the losers skip outright and do not settle for delivering a second mail, otherwise the stream would hear the same thing read out several times. If the mail did not go out (inbox write failed), the clock is rolled back to exactly the value just read, and the rollback condition is "the advanced value is still there", so it never overwrites the clock another driver just pushed up in this round. smoke **§26** pins this: two drivers concurrently scanning the same due row deliver exactly one mail (paired with a control assertion that "the concurrent round really did the work"); when the inbox write fails it faithfully reports this schedule's error and rolls the clock back, and once writes recover the same due tick is still delivered -- one failure should not permanently lose this schedule.
- **Human > schedule**. A schedule mail lands in the `background` bucket like a compaction mail: while colleagues are waiting for an answer, answer the human first, and the schedule stays in the queue for the next round. A schedule never loses a round -- `catchUp` counts due ticks forward from `next_run_at`, so a late delivery does not under-count what is owed.
- **The due round is allowed to stay silent**. In the round a schedule wakes there is no human @, and the body is that stream message; if there is nothing to say, the reply is an empty body, `runTask` closes the mail as `done` and records `mode=cron, silent=true`, without shoving a "nothing to report this time" line into the stream. An empty body in a human-@-ed round is still a failure (`empty_reply`) -- a colleague is waiting for an answer, and coming back empty-handed is the same as not having worked. The two dispositions are kept apart inside the same empty-body branch.
- **Somebody must drive it even when there is no work**. The worker's `once()` originally looked only at "is there queued mail"; a quiet stream never accumulates the first mail, so a due schedule would just lie in the table waiting for a trigger that never comes. Now idle rounds also use `dueOwnerIds` to find the owners who should wake up, then tick; this step is a pure read, and the actual delivery happens inside the tick with a CAS; frontend polling already carries the owner identity when it calls `scheduler.tick`, so it naturally covers the same thing.
- **Boundaries and self-removal**. At most 20 schedules per person (the scan uses the `(owner_id, next_run_at)` index, and the cap bounds the worst-case cost of a round), minimum interval 1 minute (a schedule is proactive work, not a timer that pumps messages into the stream), and the employee must belong to the owner and be in this very stream (scheduling someone else's employee is burning someone else's Key). When the scan hits a schedule whose employee has already left the stream, the CAS writes the clock to paused rather than advancing it: this schedule can never run again, and continuing only means a wasted scan at every due tick. Deleting an employee also deletes the schedules under their name; disbanding a stream also deletes the schedules in that stream (keeping the rows only delivers, on schedule, mails that must fail, or mails for a stream that no longer exists); deleting a schedule also retracts the one mail still unrun in the queue, but only `queued` -- the one currently generating is allowed to finish, cutting it off is `scheduler.interrupt`'s job, and deleting a schedule should not overreach and cut someone off.
- **The UI's "next time" is computed server-side**. Each `cron.list` row carries the next three due ticks, and `upcomingOccurrences` steps forward from this row's own clock; it does not re-anchor on "now" -- re-anchoring on now would describe the "every half hour" schedule as 10:37, 11:07 when it really wakes at 10:30, 11:00, and not even a minute may be off, because once it is off nobody trusts this table again. Paused returns an empty array and the UI writes "next -", rather than pretending it is still running.

### 3.6 Relay: the @ in an employee's reply is handed to the next one

Once an employee finishes a reply, the body is reverse-matched to `@name` against this stream's members (`matchMentions`), and the employees named are delivered by `fanout` as ordinary `mail`; `meta.hops` is **the previous mail's hop count plus one**, and `meta.from_agent` records who passed this baton. Still the same `mail`, still the same tick, so concurrency slots, CAS, interrupts, compaction and trajectories are all reused -- the same technique as 3.4/3.5.

- **Cap of 3 hops; the mail that hits the cap closes as `failed: hop_limit` and does not post to the stream**. Two models @-ing each other could keep talking forever, and every hop pays for one real call; the cap is decided inside `runTask` after assembly and before the request leaves the network, so the mail that hits the cap never even connects to the upstream. A human @-ing again starts over from `hops=0` -- the cap stops this chain, not this employee.
- **Three kinds of @, each with its destination**: @ another employee → deliver a task; @ a human → into that person's virtual inbox (a delegate is counted separately as usual); @ itself → recorded in `mentions` so the stream can see it, but no task is delivered, otherwise a delegate or self-questioning would assign work to itself. A name that does not match a member of this stream, or an employee in `paused`, likewise delivers nothing -- delivering it would only produce a mail that must fail.
- The floor for this section is in smoke **§30**: one hop's `hops`/`from_agent`, three hops touching the cap, only 3 replies left in the stream, and the "do not deliver" for @-ing itself / not in this stream / disabled -- each one paired with an allow assertion at the same position (swap in Employee B, who is active in the stream, and the baton is caught; flip back to active and it is still delivered). B3 in the load test `dev/bench.mjs` measures this chain's end-to-end latency, which is a different thing from §30: one proves the disposition, the other proves speed.

## 4. Execution layer: streaming + interrupts

- Upstream calls go over SSE, accumulating `delta.content` chunk by chunk; **only the body is accumulated** -- a reasoning model's thinking field never enters the stream (the stream keeps only the conclusion reached after thinking).
- Every chunk received asks `interruptWatcher` once: in-process it is hit immediately via `fireInterrupt` from `bus.mjs`; across processes the 400ms inbox polling is the backstop. On a hit it calls `reader.cancel()` and throws `Interrupted{partial}`.
- The half-finished content is not lost: on the rerun it is fed back as a hint that "the previous message was cut off mid-sentence"; a stop request sets the task to `cancelled` and the half-finished text never lands in the stream.
- Interrupt reruns are capped at 2, so two people taking turns interrupting cannot turn the task into an infinite loop; when the cap is hit, this mail and every one before it whose @ was swallowed gets a `cancelled` receipt (`meta.receipt="steer"` carries the original mail id), leaving no dangling unread in the stream.
- **The background collapse and merge round does not take interrupts**: mail whose `meta.kind` is `compress` / `dreaming` is a one-shot question, not a single character goes into the stream, so there is no half-finished body to cut off. Registering an @ that lands on such a mail as "already digested by this round" means that message has neither a task row nor a receipt -- it was quietly swallowed; and `scheduler.interrupt` picking it up and replying "already cut off" is a fake success. The determination has exactly one home (`interruptibleMail` in `functions/util.mjs`); the delivery side and the stop side read the same copy, and smoke 8c4 pins both halves with a control: that @ is scheduled as a new task and runs to completion as usual, the compaction mail still closes `done` and the watermark still advances.
- **Channel differences are written on one manifest**: [functions/backends.mjs](../../functions/backends.mjs) gives each backend channel a `transport` and `caps.tools`, and the execution layer only fetches routing from the dispatch port in [functions/agents.mjs](../../functions/agents.mjs) by transport (`chat` / `demo` / `cloud`); a transport declared in the manifest but not implemented throws at module load, rather than surviving to runtime as an upstream error.
- **Tool injection looks at `caps.tools`, not at the channel name**: for a channel that does not take tools, `tools` is `null` in the request body and the connector-tool step is skipped outright -- handing it tools wouldn't call them, it would just pay for a round of tokens; on the prompt side the same field decides whether the wording is "call tools on demand" or "write the conclusion straight into the body" (the `backend.tools` slot).
- **Delivery cards are published only at the commit point**: the `present` tool only registers this stream's stream files into this round's `presented` list (`withTools`), and the card lands together with the `insertMessage` of that reply; if there is an error mid-way or a stop request, there is no such reply and therefore no card, even if that step in the trajectory is `done`. A round that only delivered files and wrote not a word in the body counts as success under `mode: "delivery"`, and the round a schedule wakes also takes precedence over silence -- otherwise the work is finished but invisible in the stream. This column is read only by the client; it is not selected when assembling context fetches messages, so delivery notes never enter any model request (`dev/smoke.mjs` section 27 pins it with a sentinel marker).
- **A stream that breaks half-way is not "finished"**: if the SSE reaches its end with neither `[DONE]` nor `finish_reason`, the round records `upstream_stream_incomplete` and closes as failed, and not one character of the half-finished body lands in the stream. This is a different thing from "cut off by an interrupt": in the latter someone takes over, in the former the upstream simply dropped. The cloud channel has always reported `qca_stream_ended_unfinished` under this reading; the self-hosted channel used to treat a broken stream as finished -- the stream was left holding a sentence missing its tail while the inbox still said `done`.
- **Failure codes get their name at the source**: when `chatCompletion` gets a non-2xx it immediately uses `upstreamCode` from `functions/agents.mjs` to turn the status code into an `upstream_*` code; the inbox, the trajectory and that UI line "this one did not complete" all read codes produced by the same function, instead of each writing its own mapping or landing a bare `"500"`.
- **There is no automatic re-delivery**: the claim only goes from `queued` via CAS, `reapStale` collects runaway `running` into `failed`, and no path ever re-queues a `failed`. So the failure message says "to try again, @ them again", not "it will retry automatically later" -- the first is deliverable, the second is not. smoke section 28 pins these three bad dispositions with a fault switch (the 500 / eof / half tiers of `scripts.chat` in `dev/smoke.mjs`, switched per run, not by trigger keywords), paired with a control where flipping back to normal and @-ing again runs successfully.
- Once the CLI executor is wired in, the cut-off semantics change from "cancel the read loop" to "kill the process group + salvage the half-finished text incrementally from stdout".

## 5. Context assembly and compaction

### 5.1 Block order is cache order

`buildContext` produces one system + one user message each round; which blocks the system message is built from, and in what order, is written in the `PROMPT_SECTIONS` slot table in [functions/prompt.mjs](../../functions/prompt.mjs), not pushed onto the end in the engine code. Provider-side prefix cache hits by "longest match from the start", so position is an allocated resource: first bucket by `volatile` (stable blocks in front, blocks that must change every round pushed to the very back), then sort within a bucket by `order` ascending. A slot whose build returns an empty string drops no block, which is equivalent to the old `filter(Boolean)`.

| Slot id | order | volatile | Content |
| --- | --- | --- | --- |
| `identity` | 10 | No | Identity (name / role / stream name) |
| `backend.tools` | 20 | No | The notice dropped only when this channel does not take tools (`caps.tools` lives in `functions/backends.mjs`) |
| `signature` | 30 | No | Personal signature |
| `guide` | 40 | No | Working rules |
| `announcement` | 50 | No | Stream announcement |
| `skills` | 60 | No | Skill list, each entry with its provenance (built-in / platform skill / local upload / remote source name + slug + snapshot version) |
| `history.access` | 70 | No | The fixed line "call a tool if you need earlier records" |
| `memory.owner` | 78 | No | The owner's global memory (the one merged across streams, 5.4) |
| `memory.common` | 80 | Yes | common long-term memory (the latest 20, **ascending**) |
| `summary` | 90 | Yes | This stream's compaction summary + watermark |
| `transcript` | 100 | Yes | The recent transcript window (by character budget, **appended at the tail**) |
| `memory.stream` | 110 | Yes | This stream's memory notes (the latest 30, **rendered ascending**) |
| `delegate` | 115 | Yes | Delegate notes (delegate rounds only) |
| `cron` | 118 | Yes | Schedule notes (rounds woken by a schedule only) |
| `trigger` | 120 | Yes | Trigger message |
| `steer` | 130 | Yes | Interrupt prompt (interrupt rounds only) |

Gaps are left between `order` values: adding a block means claiming a number from the table, not inserting at some array index. The table self-checks at module load (duplicate id / missing order / missing build throw on the spot), so "declared but never assembled" cannot become a cache degradation you only notice at runtime.

The `memory.common` and `transcript` blocks use ascending order / tail appending so that new content only appends to the block's tail and does not break an existing prefix (descending would rewrite every new memory into the block's head).

**The trade-off in `memory.stream`**: every time a reply is finished, one `#NN reply: <first 200 chars of the body>` echo is inserted into this stream's memory. At assembly, entries are pruned from both ends by their number -- those with `NN ≤ watermark` are already folded into the summary, those with `NN ≥ window head` are carried in full in the transcript, so only echoes that fall in the gap "not covered by the summary, doesn't fit in the window" are listed separately. This block sits after the transcript, and **the prefix cache is a single cut**: past the breakpoint, even byte-identical content counts as a miss, so keeping this block empty as a rule matters more than making it small (measured: at one point it accounted for 86% of the per-round miss, see P9). Non-echo notes (compaction failure traces, things the user explicitly asked to remember) have no number and are always kept.

**`delegate` only drops on delegate rounds**: on non-delegate rounds its build returns an empty string, an empty string drops no block, and the assembled result is byte-identical to before this block was added -- the delegate feature adds no cost whatsoever to ordinary rounds' cache. The breakpoint position is unaffected by it (`CACHE_BREAKPOINT_ID` is the first volatile block in the table, at `memory.common`, pinned by smoke 8d2); it only adds one body section after the breakpoint and before the trigger message. This block's content is an internal prompt, and the red line against it entering the stream body is guarded by where the excerpt comes from: the demo model quotes only human messages from this round's context rows, and it receives the rows themselves rather than the assembled body, so the working rules, the delegate notes and the trigger message never get a chance to show up (this is exactly how the local fake upstream exposed it, smoke §25 has the assertion). Replies also quote only human messages: an employee's own reply is multi-line and carries the previous round's excerpt inside it, so scanning the body line by line would take those second-hand lines as new facts and the reply would end up repeating itself.

**`cron` only drops on the round a schedule wakes it**: positioned after `delegate` and before `trigger`, its build returns an empty string on non-schedule rounds, so the request body of an ordinary round stays byte-identical; this block marks itself `volatile` as well, so it falls after the cache breakpoint and an employee with several schedules does not break the usual prefix. Its content contains a sentence specifically against repeated announcement: the body of the due round is that stream message, and unless it says plainly "do not send another one", the model calls `send_message` first and then copies the same sentence into the body, so the stream hears the same thing read out twice (this happened the very first time the local real upstream ran a 1-minute schedule). The trigger block in the same round also changes its framing -- "nobody @-ed you, this round is your own schedule waking up", it does not pretend to be a re-sent task.

**How to locate a drop in the hit rate**: at the end of each model round, the list of slots actually dropped this round (the `[id, charCount, volatile]` triples) is written into `run_steps.detail.prompt_slots`, and the trajectory inspector's "Context" tab on the employee detail page lays them out in the original order and marks "breakpoint" on the first block rewritten every round. It records only the accounting, not the body -- the body is already in the store, and storing it again would only inflate the database.

### 5.2 Window anchors: replies take the tail, compaction takes the head

`history()` takes pages (200 rows/page, at most 50 pages) backwards from the watermark side until the character cap is reached; **it does not cut by row count**:

- **Replies use `anchor=tail`**: take the newest stretch after the watermark (cap = budget × 0.8). Records squeezed out are queried via `search_history` / `read_window`, and the prompt already says so.
- **Compaction uses `anchor=head`**: take a **contiguous** stretch forward from the watermark (cap = max(4000, budget × 0.12)). This way `older` (the older half) is necessarily a real prefix after the watermark, and `covers_through_seq` never counts records the summary never read as covered. This stretch is also taken by a **floor row count**: when there are fewer than the minimum 4 rows of a batch the character cap does not apply, otherwise a single long post could fill the whole batch (see 5.3). The reply path has no floor, because it does not prune -- a floor there would shove over-budget raw text straight into the request body.

When the window is not filled (`truncated`), the same round delivers a compaction mail to push the watermark up.

### 5.3 Compaction drains itself in the background

Compaction is not on the critical path: the reply round only does deterministic character trimming, and compaction is handed to a background mail with `meta.kind="compress"`. When a compaction mail finishes, if there are still records behind the watermark it **delivers the next one to itself** (call `finish` first, then deliver, otherwise dedup sees itself), so the backlog drains in the background in batches without waiting for a human to send another message. Only one batch is collapsed at a time (≤ 12% of the budget), to avoid cramming a hundred-plus thousand characters into a single 400-token summary.

**Pruning comes before the summary; one long post must not starve a whole batch.** The ingest cap is 8000 bytes (Chinese counted at 3 bytes each, so about 2600 characters per message; an ASCII log body can reach 7900 characters), while the smallest budget tier gives a batch only 4000 characters. If the first record right after the watermark happens to be a long log, that one record fills the batch: when taking records the first row is always kept (a window cannot be empty), the second row then breaks the cap, so this batch always has exactly 1 row, never reaches the minimum row count for collapsing, the watermark does not move a step, and the reply window is squeezed to 1 row by the same post -- this stream's summary can never collapse again, and nothing reports an error. Both places changed together: taking records honors a floor of 4 rows (when the batch is under-filled the character cap does not apply), and before collapsing each row is additionally pruned to a **row width** = this batch's budget ÷ minimum rows (1000 characters on the smallest tier). Only the copy fed to the summarizer is pruned; not a single stream original is touched, the tail of a pruned row keeps a line "...(truncated, this row is N characters, full text available by #number)", and `search_history` and `read_window` both get the full text back; the collapse step's note faithfully records how many rows were pruned and the row width, so "the summary is not reading the full text" is visible in the trajectory rather than only in the document. smoke **8c3** pins three things: the watermark still advances when a long post blocks the way, no row fed to the summary exceeds the row width, and a batch of normal-length records has not a single row cut (pruning is not an unconditional cut).

**If it cannot be collapsed, the watermark must not be raised**. The ordinal range of the batch being collapsed (`covers_from`–`covers_to`) is recorded in the compaction step's detail, and the summary row lands `covers_through_seq = covers_to` -- "covered up to #N" is a claim that can be reconciled, not a number you can only believe. An upstream 5xx, or an empty body in the reply, both mean nothing at all was folded into the summary: this step is recorded as failed (the empty-body code is `summary_empty`), the whole background mail closes as failed, **the watermark stays exactly where it is**, and this stream's memory keeps one visible note (when the same batch keeps failing only the latest note is kept: `removeAll` first clears notes with `source="compression"` and then writes, because `remove` goes through maybeSingle and would error outright on the hosted database once the condition matches multiple rows). This way the batch is still in the window next round, and "collapse it again" can actually be honored. The old writing raised the watermark even on failure and appended "folded out of the context window" to the summary's tail -- the records were in neither the summary nor the window, and that sentence was something nobody could ever honor. smoke **8c2** pins this with the three scripts 5xx / empty body / recovered-to-normal, and checks that the successful batch's `covers_from` exactly connects to the next record left uncollapsed last time and that every number in the range really exists in the stream history.

The summary body itself also has a cap (about 10% of the budget, minimum 600 characters); past it, the oldest end is trimmed off. So the accurate reading of `covers_through_seq` is "this batch has been handed to the summarizer", not "every original is still in the summary" -- the originals are always in the `messages` table, and `search_history` and `read_window` get them back.

### 5.4 Cross-stream merge: folding every stream's summary into one global memory for the owner

One employee often works in several streams at once, while the summaries folded out by 5.3 are **stored one per stream**: cross-stream stable facts ("this person's project deadline is at the end of the month", "we agreed last time to use psql, not an ORM") are scattered across the stream summaries, and none of them knows the others. What the merge (dreaming) does is feed **each stream's summary** under the same owner to the model once, fold them into one "owner's global memory", land it on the owner-level row in `app.memories`, and have it come back into every stream's request body in the next round as the `memory.owner` slot (5.1).

- **It eats summaries, not transcripts**. The input is the one summary at each stream's current `covers_through_seq`, not raw messages: transcripts run to tens of thousands of characters per stream, and one merge would have to fit dozens of streams into a single request body, at which point the budget is uncontrollable immediately; a summary is a fact already compressed one layer down, which is exactly the layer "cross-stream" needs. For the same reason **the merge comes after collapsing** -- the stretch a stream summary has not advanced to is invisible to the merge.
- **Three entry points, one execution path**. ① merging as a follow-up once a stream's collapsing is done (`users.prefs.dreaming_auto`; the switch hangs on the **owner** rather than on the employee, because the memory the merge produces belongs to the owner); ② a schedule reaching its due tick (`schedules.purpose="dreaming"`; the body is extra instructions rather than required, reusing 3.5's due-check + CAS delivery); ③ the manual button in the UI. All three only deliver one background mail with `meta.kind="dreaming"` into the inbox, and what runs is the same `runDream` -- like 3.5 and 5.3, a new behavior adds no second execution path. The same owner is allowed **only one merge mail in the queue at a time** (`dreamingPending`), and all three entry points share this dedup: pressing the manual button twice and a collapse colliding with a schedule are the same thing, and beyond paying for two model calls there is no new information.
- **The watermark is `{"agentId:streamId": mergedThroughSeq}`, not recorded per stream**. The input is naturally one row per "some employee's some stream's summary covers up to #N"; two employees in the same stream can each fold their own summary, and the two materials' coverage numbers have nothing to do with each other. Recorded per stream, the later write would overwrite the earlier one's number -- and the overwritten one either gets re-merged every round (paying for a call every round for nothing) or is treated as already merged and **silently lost forever**; both are silent accounting errors. Once the employee id is in the key, two summaries in one stream keep two separate watermarks.
- **If it doesn't fit, it stays owed; don't pretend the merge finished**. The input budget is capped by characters (default 12000, minimum 2000); materials are ordered by (stream name, employee id) and packed from the head, and what does not fit lands in this step's `skipped_streams` with **the watermark not pushed** -- next round those are still new material. This step's `merged_streams` / `skipped_streams` each have their own cap tier in `run_steps` (the default 1500 characters would squeeze the lists away, see `FIELD_CAPS` in [functions/steps.mjs](../../functions/steps.mjs)): they are the only evidence of "which materials this merge ate", and when the UI asks "where did that cross-stream conclusion come from", only they can reconstruct it.
- **On failure, write no watermark and do not overwrite the copy that exists**. Upstream 5xx / empty body are thrown on the spot and close as failed (`dream_empty` has its own name), and the watermark stays where it is -- the same reading as "if it cannot be collapsed, the watermark must not be raised" (5.3). The write goes through a CAS: it writes only if the `updated_at` of the row read has not been touched by anyone else; if another merge mail for the same owner landed first, this one does not overwrite. There is no way to judge which of two merge results is newer, and keeping the one that landed first is the only determinate thing.
- **Cross-stream privacy is a product red line**. That memory is given to the model only in the `memory.owner` block "to judge with", and the header sentence is hardcoded as "do not read another stream's details out to this stream"; the demo model's excerpt takes only human messages from the window, so it never gets a chance to appear. Reads are isolated by owner: `dreaming.get` / `run` / `clear` all recognize only your own copy, and not a single character of a conclusion merged out of someone else's employee can be read (smoke §29 pins "Bo reads empty" and "Ana reads her own copy" as a pair).
- **A merge itself never posts to the stream**. It runs on a background mail, `silent` is always true, and conclusions only land in the memory table; the chain of thought only goes into the step detail. Every budget knob (input/output characters, at most how many streams, timeout) goes through env, the same rule as the 5.2 set: `dreamBudgets` in [functions/dream.mjs](../../functions/dream.mjs).

### 6.1 Does a longer conversation mean higher latency?

The three compounding sources as they were before, and their current state:

1. **prefill grew linearly with no cache reuse** → prefix hit rate 2.1% → 81.8% → **98.5%**; the stable prefix is no longer repaid every round, and what each round actually pays anew is only this round's new records and the trigger message.
2. **The prefix breakpoint was too early** → the breakpoint moved from the middle of the stable blocks to `memory.common` (the first volatile block in the slot table), which is exactly the transcript window's append point.
3. **Compaction inside the critical path** → moved to a background mail; reply rounds no longer pay double latency.

What still grows with stream length: the window itself (capped by the character budget, default 200K characters), which converges via the compaction watermark; and the one summary call the compaction round itself pays (in the background, not blocking the reply).

### 6.2 Why it cannot reach 100%

98.5% is already pressed against the physical floor; the remaining 1.5% breaks down as:

- **This round's new content** (the new message + my previous reply appended into the transcript, measured 45 characters): by definition the prefix cache is "longest match from the start", and this round's request must carry something the previous round did not -- this part is a miss by nature.
- **The trigger message block** (measured 23 characters): it is this round's task, different every round, and can only be placed last.
- **Provider-side block quantization**: caches hit at a fixed granularity (DeepSeek 128 tokens, vLLM prefix caching `block_size=16`, Anthropic requires an explicit cache breakpoint), so the last partial block always counts as a miss. Character-level LCP is an optimistic upper bound.
- **TTL**: the prefix cache has a lifetime (minutes). If the stream @-mentions this employee once every two hours, the cache went cold long ago -- that has nothing to do with how the prompt is written; it is the real ceiling of chat-style low-frequency, long-interval load.
- **Not shared across streams**: switch to another stream and the common prefix is only 44 characters (it breaks at the stream name), because the skill list carries the segment specific to this stream. Each (employee, stream) is an independent cache entry -- that is the design intent, not a defect.

So the right reading is "**each round only pays prefill for what this round added**", not 100%. What smoke 8d locks is exactly this: reusable prefix ≥95%.

**Do not mix the two readings**: 98.5% is the character-level longest common prefix of the request body (the optimistic upper bound locked by smoke 8d, indifferent to the provider's mood); the token hit the upstream itself reports is another tier -- the statistics bar at the bottom of the employee detail page's Stream flow aggregates `run_steps.input_tokens / cached_tokens` per stream, and measured on real local DeepSeek traffic, 19 rounds gave **60.1%**: within one mail the 1st round is only 40%, later rounds 93-94% (R1's reshuffle really is working), and the rounds that drop back into the 40%s are rounds where the window moved and the prefix broke half-way. The two differ by nearly 40 points, and the gap is precisely the combined effect of "block quantization + TTL + independent per stream" above. Statistics count only model rounds where the upstream reported both input and hit counts: rounds cut off by an interrupt end before the trailing usage block, the QCA cloud and the demo backend do not report usage at all, and the UI faithfully writes "this backend does not report usage" instead of passing 0% off as a measurement.

**Sub-buckets clear the accounting before they are booked**: `cached_tokens` and `reasoning_tokens` are sub-buckets of their corresponding totals, and third-party and self-hosted gateways' `*_details` readings vary wildly -- when one is reported larger than the total it is collected as null, meaning "not reported" (`normalizeUsage` in [functions/agents.mjs](../../functions/agents.mjs)). This way the hit rate on the UI and the statistics bar can never exceed 100%, and that out-of-range dirty number is never thrown into the denominator either. `total_tokens` is not stored as a column: it equals input + output and no reading anywhere needs it. smoke section 20 pins the three tiers with the shapes "only the total is reported", "a sub-bucket out of range" and "no usage block at all", paired with a control that "collecting the reading as empty does not stop the round from finishing".

Three conclusions read out of this round's data:

1. **Effective concurrency = min(number of queued streams, budget × 3 worker concurrent rounds)**. At budget 2 the bound is 6, measured peak 6; at budget 8 with only 8 streams the bound is 8, measured 8 (derivation and measurement agree). 3. **Bursts are no longer blind**: after the P10 fix, in every one of the 8 streams × 3 mails the k-th call's context can see the (k−1)-th reply, and the order replies land in the stream matches the delivery order stream by stream.

## 8. Acceptance readings

- **Stable prefix** ≥ 95% of this round's request body (locked by smoke 8d); the current measurement is **98.5%**. The reading is "each round only pays prefill for this round's added records and the trigger message"; 100% is physically impossible, reasons in 6.2.
- **Window continuity**: the reply window's first number === `covers_through_seq + 1`, with no gap in between that is both invisible and not covered by the summary (locked by smoke 8c).
- **Preemption latency** ≤ 1.5s cut-off end to end (measured 127ms on the SSE path; the same reading is to be re-measured on the CLI path once it is wired in).
- **Time to first token** does not grow linearly with the message count (regression against a 500-row stream as the baseline).
- **Offline progress**: with the worker running, `mail.created_at → started_at` ≤ the tick interval + one execution round, and it does not depend on any browser being online.
- **Burst correctness**: when a single employee is bombarded by N streams nothing is lost, nothing is duplicated and nothing crosses streams, FIFO is strict within a stream; the same (employee, stream) never runs two mails at once (bench **B1** + smoke **8e**).
- **Effective concurrency** = min(number of queued streams, budget × 3), and the measured peak must land within [budget, bound]; a budget above the stream count is empty burning (bench **B1**).
- **Weight semantics**: when slots are insufficient the heavy side's average finish rank must be markedly ahead and the light side must not be starved; when slots are plentiful no strict priority may be asserted (bench **B4** locks both directions).
- **Multiple drivers**: with frontend polling and the worker in parallel, duplicate executions must be 0 and `slice_count` must be 1 everywhere (bench **B5**).
- **Block order is allocated**: the slot table's ids are unique, orders complete, builds complete, and the first volatile block is the cache breakpoint (locked by smoke **8d2**); the same check matches the assembled block order and body verbatim.
- **Answering on behalf opens no second path**: delegate tasks and ordinary tasks share the same table and queue, and non-delegate rounds' prompts stay byte-identical (smoke **25**: a non-delegate round does not drop the `delegate` block); one @ assigns at most one mail (each of the two loop guards is paired with an allow assertion), and the human's own notification is not lost because of answering on behalf (**answering on behalf is not receiving on behalf**).
- **Schedules open no second path**: a schedule at its due tick only delivers one more ordinary `mail`, same table and queue, and non-schedule rounds' prompts and request bodies stay byte-identical (smoke **26**: a round that is not a schedule does not drop the `cron` block). One due tick may have only one mail -- the CAS advances the clock, so of several drivers scanning at once only one wins; a failed delivery must roll the clock back and the due check runs again next round (same section). However many due ticks are owed, only one mail is delivered, the extras are recorded in `merged_runs` and in `cron.merged` in the mail, and both the UI's "merged in total" and its "next time" come from values computed server-side (when paused, "next time" is empty rather than pretending it is still running). Human > schedule: if this round has a human @, answer the human first and the schedule catches up on time from its clock in the next round.
- Each model round drops the round's `[slotId, charCount, volatile]` list into `run_steps.detail.prompt_slots`, and the trajectory inspector's "Context" tab shows them in the original order with the breakpoint marked; automatic collection of prompt character counts and the previous round's LCP still awaits R3 / the trace table.
