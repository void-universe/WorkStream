# WorkStream · A collaboration desk for humans x virtual employees

**English** · [简体中文](README.md)

WorkStream is a site application: human employees register with an email address and create their own virtual employees (each employee binds an independent API key and OpenAI-compatible endpoint, and can also be re-hung on a Qoder Cloud Agent), create streams (searchable by UUID with join requests), @-one-another in streams, stream files and stream announcements; everyone can register several SSH office machines and grant them to streams; virtual employees' tasks enter their own virtual inboxes, and the backend advances them in parallel across streams by time slice; you can also put a timetable on a given (employee, stream) pair so that at the due tick the employee wakes up and does the work itself, without anyone @-ing it; when the context is exceeded the history is compacted per stream, and old messages in a stream can be re-queried over MCP. The Market's skills tab lists two inventories — the local market and remote skill sources (the built-in WorkStream platform skill and the DevStream stream-files-and-announcement skill are visible by default); once installed into an employee, the skill instructions are injected along with the context, and every entry carries its provenance (built-in, platform skill, local upload, or the remote source's name plus slug and snapshot version; deleting a source deletes only the source — skills already copied locally stay in use and the provenance honestly reads "deleted source"). The plugins tab can connect external standard MCP services, whose tools are merged into the tool inventory of every employee under the owner. A human can also set themselves a **delegate**: pick one virtual employee under their own name to catch @-mentions on their behalf in all streams, immediately or over a time window, with per-stream on/off, and employees on self-hosted endpoints as well as Qoder Cloud Agent employees can serve as delegates.

The home page is the Stream panel: streams are streams, laid out as a card grid or a list, with a 2/4/9 split-screen switch in the top-right corner putting several streams side by side on one workbench, every cell able to @-assign work directly; creating a stream and joining by UUID open from the panel's top bar. Virtual employees, Market, the dispatch console, the virtual inbox, VMs and Settings all live in the top navigation bar and no longer occupy a left sidebar. A stream's border flashes with task status: **yellow** means work was @-assigned in the stream and the task is still queued waiting for a time slice; **green** means a virtual employee just claimed it and advanced the stream (a finished green is kept for a few seconds). The rhythm follows human feel: yellow is faster (0.65s, ≈ exercise heart rate), green slower (1.8s, ≈ resting heart rate); each stream can change these two colors individually under Settings → Blink color, and the preference is stored only on the local machine.

Both human and virtual employees can set an avatar: upload an image under Settings → Account or in the Virtual employees profile, and the browser crops it to a 128×128 WebP stored in the database, with the stream, member lists, dispatch console and top navigation all following; with no avatar set it falls back to the first letter of the name. Without an image at hand you can also click the row of built-in default avatars below the upload button (boys: short hair / side part / glasses; girls: long hair / shoulder length / ponytail) — the images are SVGs written into `src/lib/avatars.ts`, and only on click does the browser bake them into the same 128×128 WebP, so the stored column, the `avatarData` validation and the upload path are exactly the same as for an uploaded image, and the repo holds no avatar image files. Avatars and data are live state: clicking any virtual employee's avatar opens the `#/agents/<id>` detail page, showing which message their virtual inbox is processing and how many mails are still queued; a spinner on the avatar's corner means busy, and the signature hangs next to the avatar in small quoted text. Every @ message is tagged with this employee's delivery status — queued = **unread**, started = **processing**, finished = **read**, failure/cancellation marked separately. The owner can change the signature on the Virtual employees page, and the employee itself can update it with `set_signature` inside its tool loop. A non-owner opening the detail page sees only what stream members already see — the profile and presence in shared streams; keys, system prompts and memory never appear.

The right side of the chat holds two collapsible cards: the **stream announcement** (publish/clear, shows the update time, read-only for non-admins) and **stream files** (click a file name for online preview, download, upload, delete), and only below them the four tabs Members / VMs / MCP / Settings. Stream files are stored as text capped at 400KB, and an upload broadcasts a system message in the timeline; `.drawio` flowcharts are drawn as structure diagrams in the online preview (only nodes, edges and labels are restored — styles and coordinate precision are not), and all other types preview as plain text; Settings → Stream announcement keeps only a pointer sentence, so two places never edit the same field. Stream files handed in this round by a virtual employee hang under their reply as a **delivery card** (file name, size, type plus one delivery note), the whole block clickable, opening the preview of that very original in the stream files page; a round that delivered only files with an empty body still sends the card, in which case that message is a card with no bubble. Every announcement and file operation can be done through MCP tools (see "Skills and MCP" below). Machines that were granted in the stream and have a console gateway address filled in add an **SSH console** entry to the top bar, and each row of the stream-settings drawer's "machines attached to this stream" column can open it directly: in a wide window it is a real split screen (chat and input stay usable on the left, an iTerm-style terminal on the right); in a narrow container the terminal covers the whole stream and closing it returns. The console connects to the ttyd gateway on that machine, recommended started as `ttyd -p 7681 tmux new-session -A -s work` — then you and the virtual employee attach the same tmux session, so you can `dmesg -wT` and `ls` to watch the scene while watching what they do. Remote desktop is not on this chain.

Below "which message is being processed", the employee detail page draws a **Stream flow**: the horizontal axis is when each mail entered the time slice, the vertical axis lists streams by weight, high to low; each mail is a bar — processing is a yellow bar with a flowing highlight, read is colored by stream, unread is dashed, failed is red; the window automatically takes the last 15 minutes or 24 mails, and the owner and stream mates see the same chart (stream mates see only shared streams). The card's footer carries a **cache hit** statistic: each step's `input_tokens / cached_tokens` in the trajectory are summed by stream, giving the overall hit rate (token-weighted, not an average of per-round percentages) and per-stream hit rates; box-selecting a time range counts only that range; the method lives in `src/lib/usageStats.mjs` (the `.mjs` extension is so `dev/smoke.mjs` can import the very same implementation and pin it into assertions, instead of copying the algorithm again in the test): rounds where upstream reported no usage (cut off by an interrupt, QCA cloud and demo backends) stay out of the denominator, rounds reporting self-contradictory numbers are collapsed to `null` at the storage step as not-reported (`normalizeUsage` in `functions/agents.mjs`), and when there is no usage at all it simply says "this backend does not report usage" rather than passing off 0%.

A delegate only **answers on behalf**, it never **collects on behalf**: in Settings' Delegates card pick one virtual employee under your own name, choose the effect window as "start immediately" or "a time window" (up to 90 days out, and either end can be left alone), and this roster takes effect across all of that employee's streams at once; when the stream @-mentions the human, the @ notification is still delivered to the human as before (virtual inbox or real email) — the delegate merely receives one **extra** task. The reply posted into the stream is still signed by the delegate itself, with an "answering on behalf of @X" tag on the bubble, which comes from `messages.on_behalf_of` rather than renaming anyone to the human. The stream-settings drawer's "delegate for this stream" can toggle it for this stream only or switch to another employee. Whether it applies is computed from the clock at the moment of dispatch, never by changing state at the deadline: when the window ends the answering simply stops, and no resident process is needed to guarantee that "closing the sign" happens. The delegate must belong to you, be running, and already be in this stream — borrowing someone else's employee to speak for you amounts to letting a third party read your stream context, and it is refused on the spot.

Virtual employees can also **do proactive work on a schedule**, without waiting to be @-ed: in the dispatch console's Schedules card, put an "every interval" (1 minute to 7 days) or "daily at" schedule (time + weekday checkboxes + UTC offset, the local offset brought in by default and tagged "local", half-hour steps supported) on a given (employee, stream) pair, then write what needs doing (cap 2000 characters). After saving, the row directly shows the next three due ticks computed server-side (e.g. "next due · today 15:11"), when the last run happened, and the cumulative count of merged ticks. The round at the due tick still goes through the same time-slice pipeline: the schedule merely posts one more mail into that employee's inbox, and concurrency slots, CAS claim, interrupts and compaction are all reused; when someone is online waiting for an answer, the human is answered first and the schedule catches up by clock in the next round; if the round has nothing to say it may reply with an empty body, and WorkStream will not post a "nothing this time" into the stream for you. At most 20 schedules per person, minimum interval 1 minute (proactive work is not a timer for flooding the stream); pausing means writing the clock column empty, and the UI then shows "next due —" instead of pretending it still runs, and editing the text will not reopen a schedule you stopped yourself. Deleting a schedule also retracts the queued mail that hasn't run (the one already generating runs to the end — cutting it off is an interrupt's job); when an employee is removed from a stream that schedule stops itself, and deleting the employee or dissolving the stream cascades to the schedules hung on them / on this stream. Schedules can only be made for employees under your own name and streams you are in — scheduling someone else's employee burns someone else's key and is refused on the spot.

Virtual employees of one person often work in several streams at the same time, and each stream's history folds into its own summary — cross-stream facts ("this project ships at month end", "we agreed on psql, no ORM") sit scattered in per-stream summaries with nobody merging them. **Global memory (dreaming)** does this job: it feeds the current compaction summaries of all the owner's streams to the model once and merges them into one global memory belonging to that person, which comes back as an independent block into the context of every stream under their name in the next round (it sits before the cache breakpoint and is reused verbatim in steady state, adding no per-round cost). There are three entry points and all go through one merge path: **merge right when a stream's history finishes folding** (the switch on the dispatch console's "Global memory" card, hung on the person rather than the employee, because the merged result belongs to the person), **merge on a schedule** (create a "merge global memory at due tick" schedule — for this kind the body text is an extra instruction, not required, and the round doesn't speak in any stream), and **run one merge manually here**. The three entry points share one deduplication: only one merge mail per person may be queued at a time; double-clicking the button and a fold colliding with a schedule are the same thing — nothing new except paying one call. The watermark is kept per (employee, stream): when two people in the same stream each fold a summary, recording per stream alone lets the later write override the earlier sequence number, and that entry either re-merges every round or is treated as merged and missed forever; the summaries that don't fit the input budget in one go are honestly recorded as "not merged in this step", the watermark does not advance, and next round they are still new material; an upstream error or an empty-body reply means not one stream was merged, so no watermark field is written, and it also never overwrites what someone else landed first (compare-and-write). Cross-stream privacy is a hard boundary: that memory is for the model's judgment only, the header sentence is hardcoded "do not recite another stream's details to this stream", it never enters stream chat bodies, and when others read their own copy they read emptiness.

The light and dark themes are controlled by `<html data-theme>` + Tailwind `dark` variables; the first-frame script in `index.html` pre-sets it from the localStorage preference or the system preference to avoid a white flash. The `>_` in the top navigation can switch between "solid block" and "inset" under Settings → Logo style: the inset one has a transparent background, white glyph in dark theme and black in light, and the preference is stored only on the local machine. The copyright line `copy right www.void-universe.com` is written on the About page and the login page footer.

The UI languages are the deduplicated official/common languages of the top 26 economies by nominal GDP, listed as **18** (IMF WEO 2025 figures, April 2026 edition: en, zh-Hans, de, ja, hi, fr, ru, it, pt-BR, es, ko, tr, id, nl, ar, pl, sv, he). This set is decided by one inventory and lands in two places: the frontend [src/lib/i18n.ts](src/lib/i18n.ts)'s `LOCALES` carries id, endonym, writing direction and "finished or not", while the backend [functions/locales.mjs](functions/locales.mjs) carries only the id whitelist (an Edge Function cannot bundle the frontend TS, so the list is stored twice, and `npm run check:schema` cross-checks the two id sets verbatim, the keys and placeholders of the four dictionaries, and whether every key the UI looks up really has a translation). **The first time you enter the site you are asked for a language once** (preselected from the browser language; whichever you pick, all screen text changes right there — that proves it took effect better than a "switched" toast), and after login it is written to `users.prefs.lang` and read back on the next cold start — the account preference beats the local one, so switching devices needs no re-choice. So far only Simplified Chinese, English, German and Japanese are finished, and the coverage is **the whole UI's copy**: the language step itself, login and signup, the verification-link landing page, the top navigation, Settings, and the chat, virtual employees, schedules, skills-and-plugins and trajectory-inspector pages — even the error codes returned by the backend (`upstream_rate_limited`, `schedule_not_owned`, and the family assembled from field names by the validator such as `invalid_token`, or `users_request_failed` assembled from the table name when the database is unreachable) are translated, because the reason "this round didn't run" is the sentence most in need of being understood, and still reading Chinese after switching languages means the switch didn't happen. The remaining 14 are listed by name under "coming soon" but not clickable: offering an option that still shows Chinese gives the user no error at all, which is worse than not offering it; Arabic and Hebrew also wait for the right-to-left layout batch (`<html dir>` is currently always `ltr`). **The UI copy is translated; the body text generated by the backend is half translated**: the system lines that land in a stream and the demo employee's conversational replies are decided at the moment of writing by the actor's `users.prefs.lang`, with the Chinese and English templates kept together in [functions/copy.mjs](functions/copy.mjs) (an account that never picked a language falls back to Chinese, one that explicitly picked German or Japanese falls back to English — the odds of reading English are far better than the odds of reading Chinese); virtual-inbox mails, compaction and merge summaries are still Chinese, and the explanation line on the Settings page draws exactly that line, without pretending they were translated along (an inline tag would require the backend to carry the provenance on the message — see the TODO table in [CHANGELOG.en.md](CHANGELOG.en.md)). Deciding a system line's language by its writer costs one thing: when the members of a stream do not share a language, the line shows the actor's — the thorough fix is storing a structured event and rendering it per viewer locale, which needs a column on messages plus a backfill of historical rows.

## Running the whole chain locally

Requires Node 22.12+ (uses only Node's Web crypto/fetch; no Deno, and no cloud credentials of any kind).

```sh
npm ci
npm run dev:function   # local Function: http://127.0.0.1:8000/functions/v1/app (`dev:function:worker` also runs the resident scheduler)
npm run dev            # frontend: http://127.0.0.1:5173 (Vite already proxies /functions/v1/app to the above)
node dev/seed-demo.mjs # one command through the whole chain: signup -> create demo virtual employee -> register VM -> create stream -> @ -> advance time slice -> reply
npm run dev:registry   # optional: local skill source at http://127.0.0.1:8123/index.json, for verifying the remote Market
```

When `seed-demo.mjs` finishes it prints the stream UUID and the login email/password; opening `http://127.0.0.1:5173/#/` in the browser lands you on the Stream panel, where you click "enter" on a card or watch the virtual employee's replies in a split-screen cell. It uses the built-in demo endpoint `demo://local` by default (model name `demo`), so the whole flow completes without a real key; to hook up a real upstream, fill your own base URL and key on the Virtual employees page, or change the model source to Qoder Cloud Agent (see "Cloud Agent backend" below).

It also pins four things. Second, **cross-checking server error codes against the frontend's error-copy**: the count of codes is printed by this check itself and never copied into the docs; every code written literally in `functions/*.mjs` must have a dictionary key in `src/api.ts`'s `ERROR_KEYS`. But the families users hit most easily appear as no literal anywhere — they are templated from variables: `invalid_<field>` assembled by the validator from the field name, `registry_<reason>` from remote fetch failures, `skill_skipped_<reason>` per skipped entry from a skill source, and `<table>_request_failed` assembled from the table name when a database read/write fails in [functions/store.mjs](functions/store.mjs). A literal scan is blind to all of these, so this cross-check first recognizes "code-shaped" templates by form (exactly one `${…}`, the static segments on both sides left with only `[a-z_]`), then expands what literals the variable can take in the code using a source table (field names from the validator call sites and signature defaults, reasons from `code:` and `note()` literals, table names from the migrations), and looks the expanded real codes up in the copy. Three situations fail on the spot: a new function outside the signature table that assembles `invalid_<field>`, a registered source table that yields not one value, and any spelling outside `NOT_CODES` that nobody registered (that table is the list of shapes that look like codes but are not — `call_<id>` is a tool-call id, `<field>_clipped` is a length field in the trajectory, each stating why it is not an error code). A code without copy means pasting an internal field name or table name straight onto the screen. Third, **two copy expressions side by side need a separator**: a Chinese sentence ends with its `。` and segments itself, Latin scripts need a space; putting two lookup expressions on adjacent lines in JSX without a {" "} separator between them looks fine on the Chinese UI and renders as `…follows it.No delegate…` in English, and this check recognizes the shape and reports it (the delegate line in the stream-settings drawer really did ship without that one space). Fourth, **the Chinese/English pairing of the browsable documents**: README, CHANGELOG and docs/arch/scheduler each have an English twin, and the two link to each other from a line at their own top; what this check compares is shape, not a word-for-word translation -- heading level sequence, table row and cell counts, body size, the inline-code and link sets, plus the switch link in both directions. Inline code and link targets are facts, not copy, so they stay byte-identical in both languages; the only exception is shorthand a document invents for itself (`invalid_<field>` is a placeholder spelling, no such string exists in the code), which counts as matched once its English form is registered in the alias table. Chinese left untranslated in the English copy reports on the spot -- that sentence looks perfectly fine on the Chinese UI and only shows up after switching to English, and the smoke test hits the API and never sees it. A `.md` outside the pairing table must be registered as a single-language document with the reason it only exists in one.

## Skills and MCP

- Built-in skills are written in `functions/skills.mjs`: never stored in the database, never uninstallable, always injected into every virtual employee's context:
  - **WorkStream platform skill**: creating a stream, pulling in employees, inviting humans, sending messages, registering/authorizing VMs, reading stream history and the announcement.
  - **DevStream stream files and announcements**: the complete parameters for browsing, previewing, uploading and deleting stream files and reading and writing the announcement, including `tools/call` examples for the external MCP.
- The two public default skills (weekly report and progress sync, meeting notes and action items) are filled in idempotently by fixed ids and installed automatically when a new employee is profiled.
- Market (top navigation) has two tabs. **Skills** does not expand details by default: one line per entry — name, version, category, a one-line summary and a `.md` download link — with the body shown only on click; the local market (uploaded on this site: public, settable as a default skill for new employees, installable to chosen employees along the way) and the remote skill sources each take a sub-list, and search by name/summary/category lists entries the same way. There are two install entry points: in Market you can install to one chosen virtual employee, to all existing employees, or to "existing + future employees" (that last one marks the skill as default, auto-installed when a new employee is profiled); the Skills tab of the employee detail can also search the local market and the remote sources, but what it installs goes only to that one employee, and uninstalling happens in the same tab. The built-in skill row no longer shows an install control — it is always enabled for every employee, nothing to install. **Plugins**: connect external standard MCP services (JSON-RPC over HTTP); the server probes `tools/list` and caches the tool inventory, these tools are merged into the tool inventory of every virtual employee under the owner, and calls still go through the same tool pipeline and land in the trajectory; tokens are stored only as ciphertext and the UI returns only their tails, and endpoints are validated by SSRF rules (only https in production; internal networks allowed only with `WORKSTREAM_DEV=1`). At most 12 connectors per person and at most 24 tools per connector; when a tool name collides with a built-in tool, the built-in wins.
- Remote skill sources (`functions/registries.mjs`): the owner adds registry addresses themselves — at most 8 per person, at most 200 entries per source. A source is just an index JSON with `schema: 1` — `{ name, skills: [{ slug, name, summary, category, version, body_url }] }` — where `body_url` points at a `.md` body on the same host, so a GitHub repo or static site holding `index.json` plus a few markdown files works as a skill source. Version numbers are display-only; comparisons take dot-separated numeric segments segment by segment (`1.10` is newer than `1.2`), and a non-numeric version that can't be compared counts as an update whenever it differs.
- A remote install means "copy a snapshot": at the moment of install or update the body is written into a local `skills` row along with its source (`source_registry_id` + `source_slug`) and version, and whatever upstream changes afterwards does not affect the employees using it. There is exactly one snapshot row per owner + source + slug, shared by several employees, so an "update" replaces the body once and every employee that installed it switches at the same time. Opening the Skills tab of an employee detail pulls each source's index once to self-check versions (or click re-check versions to trigger it manually); entries with an update show the target version and an "update" button in the installed list; when some source is temporarily unreachable it only notes that those remote skills cannot be version-checked right now, without affecting the injection of what is already installed. Fetch boundaries: index and body both time- and byte-limited (256KB / 200KB), redirects refused, the body must be same-origin with the index, and only https in production.
- Available in an employee's tool loop: `search_history / read_window / list_files / read_file / upload_file / delete_file / present / get_announcement / get_context / list_skills / read_skill / list_my_resources / set_signature`, plus `send_message / create_stream / add_agent_to_stream / invite_member / set_announcement / register_vm / grant_vm` executed as the owner. Write operations are checked against the owner's role in the stream and resource ownership; `set_signature` changes only the employee's own signature and is not open to the external MCP. `present` marks one file of this stream as this round's deliverable, and only makes sense inside the employee loop — the card must hang on the reply of that very turn, and an external MCP call belongs to no turn, so it is not in the external inventory.
- The external MCP endpoint (`POST /functions/v1/app?action=mcp`, authenticated by `x-workstream-mcp-key`) is scoped to that stream and exposes 13 tools: stream history, context, announcement reading, stream file list/read/upload/delete, and `send_message / invite_member / set_announcement / list_skills / read_skill`; creating streams and registering/authorizing VMs are available only inside the employee tool loop.

## Cloud Agent backend (Qoder Cloud Agents)

On the Virtual employees page the **model source** defaults to a self-hosted OpenAI-compatible endpoint, but you can also pick **Qoder Cloud Agents**: the employee then carries no model of its own and instead hangs on the existing agent in Qoder Cloud Agents. When creating the profile, paste either `agent_…` or the whole console link (the id is taken from `https://qoder.cn/cloud/agents/agent_xxx`); switching the address field to cloud auto-fills the CN-region origin (change it yourself for another region or a private deployment); the token is a `pt-…` created under Qoder Settings → Personal Access Tokens, sealed with AES-GCM into the database as before, with the UI showing only its tail. Switching backends must come with a new token — a self-hosted endpoint's `sk-` key is not recognized in the cloud, and the server refuses outright with `agent_key_required_for_backend`.

This channel differs from a self-hosted endpoint in three ways, all deliberate:

- **The context authority stays in WorkStream**: each round compresses the common memory, this stream's memory, the window after the summary watermark and the skill instructions into a single `user.message` (role segments marked; over 900,000 characters is blocked before leaving the server). The cloud session is used only as the cloud-side conversation cache, one per (employee, stream) kept in `app.qca_sessions`, so different streams never bleed into each other on the cloud; when the employee is removed from a stream, rebound to a different cloud agent, or changes address or token, the corresponding cache is invalidated and rebuilt. The background compaction round uses a one-shot session, so "summarize for me" never mixes into stream conversation history.
- **The tool loop is in the cloud**: our stream tools are not injected, and the cloud agent uses its own tool set. Consequently the skill instructions in its context change wording — "WorkStream tools are not reachable on this channel; do not write tool names into your reply; list any actions that need landing as a to-do" — so it does not fake-execute a `send_message` by following the skill body.
- **Thought chains do not enter the stream**: connect the SSE first, then send the question, and take only the blocks with `type=text` from the canonical `agent.message`; thinking and tool blocks are dropped outright. Partial deltas are used only to hand over the body up to the breakpoint when the stream is interrupted; if the stream runs out before a canonical reply arrives it honestly reports `qca_stream_ended_unfinished` / `qca_no_reply` rather than passing off deltas as the reply. Cloud errors, rate limits and dead tokens are all mapped to `qca_*` error codes in the trajectory, and the UI uses the same "this didn't complete" notice as self-hosted endpoints. The thought-chain tab of the trajectory inspector is the only entry point for seeing it: when the backend returned no reasoning, that page says "this section is empty" instead of leaving a blank that looks like a broken load.
- **Interrupt and stop use the same bar on both channels**: it asks whether to stop on every chunk received and on every 800ms of silence. A cloud agent running tools on its side may emit no deltas for a whole stretch, and checking only at chunk boundaries would drag an interrupt toward the full 180s round timeout, so silent stretches must be asked too — both backends' `Interrupted` hand over the half body before the breakpoint, and the layer above does not distinguish.
- **Upstream bad behavior is graded the same on both channels**: when an SSE reaches its end with neither `[DONE]` nor `finish_reason`, the self-hosted channel reports `upstream_stream_incomplete`, which is the same thing as the cloud's `qca_stream_ended_unfinished` — not one character of a half body enters the stream, and the round closes as failed. Non-2xx is translated at the egress step into a named code (`upstream_server_error` / `upstream_rate_limited` / …), so no bare `"500"` ever lands in the inbox or the trajectory; one sentence has exactly one home in the error-code table, read by every place in the UI. No path ever re-queues a `failed`, so the stream line says "to try again please @ them again", not "will retry automatically". Section 28 of the self-check pins these three with a fault flag (500 / empty stream / truncated, switched per run, not by trigger keywords), paired with a control that a re-@ after dialing back to normal runs fine.
- **Backend differences live on one inventory table**: in `functions/backends.mjs` each channel carries its own transport and `caps.tools`, and "does this channel take tools" is decided by that one field alone — the prompt wording, whether the engine sends a tool inventory, whether the owner's connectors are consulted, all read the same copy. A transport declared in the table but missing from `TRANSPORT_ROUTES` in `agents.mjs` throws at cold start; the UI's Model source dropdown options are cross-checked against the table by `npm run check:schema`. The built-in demo endpoint is the table's third channel: it is not an option on the employee profile — it is recognized from the address, since `api_base_url` equal to `demo://local` names it, so unworkable combinations such as "cloud backend + demo address" are blocked already at profile creation and edit (`qca_needs_real_origin`).

The connectivity test (`agents.test`) against the cloud pulls the model inventory once, confirming the token and address pair up — it creates no session and touches no usage; the other channels go through the engine's same dispatch fork with one very short conversation. Real cloud integration needs a `pt-…` token; the self-check suite covers the same chain with a local fake QCA (section 23 of `dev/smoke.mjs`), and the inventory's own shape and parsing rules have section 8d3.

## Code structure

```
src/            React 19 + Vite 8 + Tailwind 4 frontend (views/ split by page, lib/ for theme, UI language, routing and shared UI, locales/ for the dictionaries of the finished languages)
functions/      deployed as a single app Edge Function: index.ts entry + handler.mjs routing + the business modules
dev/            local fake database, Function harness, example scripts and self-checks (not in the release bundle)
sql/            0001_init.sql … 0014_vm_gateway.sql: table creation and incremental columns for the 23 app.* tables, within the subset the site migration API supports
```

Repository rules are written in [AGENTS.md](AGENTS.md) (single language by design, see the document pairing below): the environment gates, the gate floor, the registry and ordering invariants, the key boundaries, the visual acceptance criteria. Every rule points at an implementation or a gate in this repo; a rule that cannot point at one does not belong there.

Release notes and the TODO list are written in [CHANGELOG.en.md](CHANGELOG.en.md): it records only "which merge brought what" and "what is still missing"; how each capability is used remains governed by this file, which never gets a second copy of the instructions there.

The browser only calls the same-origin `/functions/v1/app?action=<name>` and carries no platform credentials. The session token rides in the custom header `x-workstream-token` — the site adapter layer strips the frontend's `authorization` and `cookie`, so those two headers cannot carry application-layer credentials (section 11 of `dev/smoke.mjs` runs the real `serveSite` and verifies exactly this boundary).

Authentication is done at the application layer: PBKDF2-SHA256 password hashing (150,000 rounds), session tokens as sha256 digests (30 days), and API keys plus VM passwords sealed with AES-GCM (the master key prefers `WORKSTREAM_DATA_KEY`, and otherwise lands in one row of `app.runtime_state`). Ciphertext columns are read only server-side, and the API returns only the tail of a key. User-supplied API addresses pass the SSRF whitelist: only https in production, internal and metadata addresses refused.

Scheduling has two driving modes going through the same `scheduler.tick`: an edge function cannot stay resident, so a pure site deployment advances one tick per 5-second frontend poll (skipped while the page is hidden); local/self-hosted deployments can add `--worker` (or `WORKSTREAM_WORKER=1`) to bring up the resident loop of `functions/worker.mjs`, advancing the inbox with no frontend open at all. Each virtual employee's budget for the tick is split across its streams by stream weight (confirmed by the stream owner/admin, equal by default) using the largest-remainder method; tasks are claimed with compare-and-write; running orphan tasks are caught by expiry reclamation; the @-between-employees depth limit is 3. Answering via a delegate opens no separate path: it merely posts one extra ordinary `mail` at the dispatch moment, reusing time slices, CAS claim, interrupts and compaction wholesale. Schedules likewise open no separate path: a schedule that comes due is posted as a mail inside the same tick, and the worker also scans due rows when not one mail is queued (keying only off "is any mail queued" means a quiet stream never accumulates the first one, and its due schedules would just lie in the table waiting for a trigger that never comes); advancing that clock uses compare-and-write, so the frontend poll, the resident worker and multi-instance Functions all seeing the same row yield exactly one winner, and a failed delivery rolls the clock back to the value just read so the next round re-decides the due tick.

## Launch status

The frontend and the Function have been verified locally as described above. Cloud publication still needs two steps, and the current account's subscription plan allows only static-site deployment and cannot enable a database and storage for this site, so enabling the backend, applying the fourteen migrations 0001→0014 under `sql/` in order (creating the new tables alongside the base ones — `run_steps`, `plugins`, `skill_registries`, `qca_sessions`, `schedules` — plus incremental columns such as `messages.presented`, `memories.covers_streams`, `schedules.purpose`, `vms.gateway_url`), and publishing the full version with the backend are all stalled at the same point. The planned storage boundaries (application-layer auth + tables read and written by the site Function, keys sealed into the database with AES-GCM) have been confirmed, and the accompanying disclosures still hold:

- The database tables are reachable from the Function; isolation against provider direct-access/bypass entry points has not been penetration-verified in a deployment environment.
- VM registration and connection probing are real (host/port/privilege level + HTTP/TCP reachability probing), but the edge runtime has no raw TCP sockets, so the server never actually logs into SSH to run commands; passwords are stored only as ciphertext and never shipped to the browser. The **SSH console** a human clicks in a stream runs on a different chain: the browser connects straight to the WebSocket gateway on that machine (the ttyd wire format), and WorkStream only stores the gateway address — it does not proxy the session and does not hand out credentials, so there is no server-side SSH channel on this chain to breach; the price is that the gateway has to be kept running on that machine by yourself.
- Email verification uses the development-mode inbox (the verification link appears directly in the UI); once `WORKSTREAM_SMTP_URL` is configured it switches to relay delivery.

`functions/` and `dist/` are ready to publish: `webDirectory: "dist"`, `functionDirectory: "functions"`, `databaseAccess: "read_write"`, `secretNames: ["WORKSTREAM_DATA_KEY", "WORKSTREAM_SMTP_URL"]` (both Secret values are entered through site settings, and both are optional).
